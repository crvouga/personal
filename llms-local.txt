# crvouga/personal — LOCAL development infrastructure guide

> **Scope: developer machines only.** Use this guide for everything that runs on or configures a computer used for development: the locked mise toolchain, workstation configuration, the container engine, the `personal` CLI, the Ubuntu developer fleet (one macOS manager, stateless Ubuntu workers), T3, the private fleet AI proxy (CLIProxyAPI), Beszel monitoring, Turborepo caching and disposable test databases. Generated from `scripts/dev/README.md`, `mise.toml`, `packages/workstation/agents/setup.md` and `packages/fleet/docs/ubuntu-sync.md`; tools and dependency graphs are pinned in `mise.lock` and `.mise/locks/`.

**This guide never covers cloud-hosted app infrastructure.** Vault/OpenBao coordinates and policies, PostgreSQL `DATABASE_URL`, the R2 object store, Railway hosting, GHCR images, DNS/TLS, GitHub OIDC and the Google sign-in auth relay are **cloud app infrastructure** → https://www.chrisvouga.dev/llms-cloud.txt. If your task is about any of those, stop and use that guide instead. Do not mix the two.

Canonical deployed URL: https://www.chrisvouga.dev/llms-local.txt · Index of both guides: https://www.chrisvouga.dev/llms-infra.txt · Source snapshot (current `main`): https://raw.githubusercontent.com/crvouga/personal/main/llms-local.txt

## Local vs cloud: the boundary

| Question | Local (this guide) | Cloud (the other guide) |
| --- | --- | --- |
| Where does it run? | A developer's computer or a fleet node | Railway, Cloudflare, managed PostgreSQL, GHCR, GitHub Actions |
| Who owns it? | mise (`mise.toml`, `mise.lock`), `packages/workstation`, `packages/fleet`, `packages/cliproxy-fleet` | OpenTofu in `crvouga/personal` only |
| How is it changed? | The documented local commands below, when the user asks for machine setup | A GitHub issue on `crvouga/personal`, then a reviewed OpenTofu PR |

Rules:

- **Nothing here provisions or changes a cloud resource.** Machine setup, `fleet-sync`, workstation sync and the AI proxy never create, deploy or reconfigure Vault, databases, buckets, DNS or Railway services. If a local task seems to need one, it is a cloud request: use https://www.chrisvouga.dev/llms-cloud.txt.
- **Machines consume cloud credentials; they do not own them.** A fleet node's Vault login, the AI proxy's encrypted R2 backup and its recovery keys in Vault are reads from cloud infrastructure. The Vault server, its policies, tokens and buckets stay OpenTofu-owned and are documented only in the cloud guide.
- **`dev` does not mean local.** The Vault `dev` config, the `dev` bucket and the `dev` `DATABASE_URL` are cloud resources. "Local" in this guide means *runs on this computer*.
- **A developer machine is never a hosting target**, and a fleet node is never an app server. Apps are hosted only through the cloud guide.
- **Global tooling changes only on request.** When the user asks for machine setup, run the checked-in bootstrap and locked mise toolchain. Otherwise report missing tools with the documented command; do not make unrelated global changes.

## Machine setup: macOS, Windows and Linux

This is the shared development setup for **crvouga/personal**. One versioned
manifest, `mise.toml`, owns the developer tools; `mise.lock` and `.mise/locks/`
own resolved artifacts and dependency graphs. Both bootstraps apply that same
manifest to the current user globally. Other projects can override versions with
their own mise configuration. No paid account or cloud secrets are needed to
install the toolchain.

### New machine

macOS / Linux, in Bash (download first so the script is reviewable):

```sh
curl -fsSL https://raw.githubusercontent.com/crvouga/personal/main/scripts/dev/bootstrap.sh -o /tmp/workspace-bootstrap.sh
bash /tmp/workspace-bootstrap.sh
```

Native Windows, in x64 PowerShell (5.1 or newer):

```powershell
Invoke-WebRequest https://raw.githubusercontent.com/crvouga/personal/main/scripts/dev/bootstrap.ps1 -OutFile "$env:TEMP\workspace-bootstrap.ps1"
& "$env:TEMP\workspace-bootstrap.ps1"
```

If script execution is blocked, use a process-scoped policy for this reviewed
script: `powershell -NoProfile -ExecutionPolicy Bypass -File "$env:TEMP\workspace-bootstrap.ps1"`.
Do not change the machine-wide execution policy. WSL is optional: run the Linux
bootstrap **inside WSL** to install Linux tools there; the native Windows and WSL
tool installations, Docker connections and credentials are separate.

Default checkout: `~/workspace`. Override with `WORKSPACE_DIR=/path/to/workspace`
on Unix or `-WorkspaceDir C:\path\workspace` on Windows. An existing checkout is
reused, never reset or implicitly pulled. From a checkout, run
`bash scripts/dev/bootstrap.sh` or `& ./scripts/dev/bootstrap.ps1`.

The scripts install checksum-verified mise **2026.10.24**, trust this repository's
configuration, install pinned Bun, install the shared tools with `--locked`, copy
the managed global config/lock/sidecars, set up persistent shims on PATH, and run
`bun install --frozen-lockfile`. Reopen your terminal/editor afterward. To refresh
an already-open Unix terminal immediately, run `exec "$SHELL" -l`; an installer
cannot change its parent shell's environment. **If `bun` or `mise` is missing,
run `bash scripts/dev/bootstrap.sh` from this checkout first, not a Bun command.**
Unix PATH blocks cover `.profile`, existing `.bash_profile`/`.bash_login`,
`.bashrc`, `.zshenv`, `.zshrc` and fish's config. Zsh uses `ZDOTDIR` when set.
POSIX blocks are quiet, idempotent
and placed before interactive-only early returns, so noninteractive SSH/agent
commands can find the same shims without loading an interactive UI;
Windows updates only the user's PATH; AWS CLI v2 additionally uses the official
versioned MSI (a UAC prompt may appear) because mise's AWS recipe supports only
macOS/Linux. Its version comes from the same manifest and its Windows SHA-256 is
pinned in `vars.aws_windows_msi_sha256`; no unversioned installer is executed.
CI/non-interactive setup never opens an elevation prompt and requires an
administrator context if that MSI needs installation. Existing unrelated mise config/lockfiles
are refused: back them up and move them first, then merge intentional overrides
using project configs. `MISE_CONFIG_DIR` and `XDG_CONFIG_HOME` are respected for
configuration; the PATH step also respects `MISE_DATA_DIR`, `XDG_DATA_HOME` and
`MISE_SHIMS_DIR`, including Windows' `%LOCALAPPDATA%` default.

Fleet's remote bootstrap invokes this same owner with a private `--status-file`
path. The JSON record contains only a version, installer phase and status, never
commands or raw errors. It is diagnostic progress, not proof of fleet readiness.
The native T3 archive verifier checks actual content, modes, links and ownership
by the development user; archive-builder numeric user/group IDs are not portable.
A mismatch leaves the running service and application state untouched.

### OS prerequisites and supported platforms

- **macOS x64 / Apple Silicon:** install Apple's Command Line Tools. If Git is
  absent, bootstrap launches `xcode-select --install`, stops, and asks you to rerun
  after installation. These tools provide Git and native compilers. `curl`, `tar`
  and `unzip` must be available.
- **Linux x64 / arm64, glibc:** Git, curl, trusted CA certificates, tar, unzip, xz
  and a C/C++ compiler/make. If Git is absent, bootstrap installs prerequisites
  with `sudo apt-get` or `sudo dnf`; other distributions receive an actionable
  error. On Debian/Ubuntu with Git already installed, use
  `sudo apt-get install git curl ca-certificates tar unzip xz-utils build-essential`.
  Alpine/musl is not in this baseline.
- **Native Windows x64:** Git for Windows (includes OpenSSH and Git Bash).
  Bootstrap installs it through WinGet if missing; without WinGet, install Git
  from https://git-scm.com/download/win. Windows ARM64 is not yet validated.
  For packages with native C/C++ addons, install Visual Studio Build Tools with
  the Desktop development with C++ workload and Windows SDK. Enable Developer
  Mode if using workstation symlink features; core toolchain setup uses copies
  and does not require symlinks or an administrator shell.

Git, OS compilers/SDKs, Docker Engine/Desktop, desktop apps, and kernel versions
are **OS prerequisites**, not covered by the mise lock. The same tool versions
are selected across OSes, using different platform binaries; this does not make
all OS behavior or every project command identical. Existing infrastructure
scripts may require Bash/Unix tooling; use Git Bash where supported or WSL for
Linux-specific workflows. Exact container builds should pin base image digests.

- **JavaScript/TypeScript:** Node **with npm**, Bun, pnpm, Yarn and Deno.
  TypeScript, ESLint, Prettier, Turbo and test frameworks remain project

- **Languages/builds:** Python (precompiled), uv/uvx, Go, Rust/Cargo/rustfmt/Clippy,
  CMake, Ninja and Just. OS compilers/linkers remain prerequisites: Apple Command
  Line Tools, Linux build-essential/GCC, or Windows MSVC Build Tools + SDK.
  Java (Temurin 25 LTS) and .NET 10 SDK are locked on-demand tools.
  Project manifests still select project-specific language/library versions.
- **CLI utilities:** ripgrep (`rg`), fd, fzf, bat, delta, jq and Mike Farah yq.
- **Delivery/infra:** Vercel, Wrangler, Railway, OpenTofu, Vault CLI (for the OpenBao-compatible secret service), Docker CLI,
  ShellCheck, shfmt, actionlint, AWS CLI v2, kubectl and Helm. Installing provider CLIs does not authorize agents
  to provision resources; shared infrastructure is still OpenTofu-owned.
- **Agent harnesses:** Claude Code (`claude`), Codex (`codex`), Gemini CLI
  (`gemini`), GitHub Copilot CLI (`copilot`) and OpenCode (`opencode`).
  Installed versions are checked by doctor on all three OSes. Start the CLI you
  want to use and complete its interactive sign-in; installation does not copy
  tokens, choose paid plans or grant agent permissions. OpenCode's optional
  settings remain managed by `personal` and Vault. Codex sign-in follows the
  [official CLI guide](https://learn.chatgpt.com/docs/codex/cli).
  Claude/Copilot background self-updaters are disabled through mise environment
  settings so they cannot silently replace locked versions; update through this
  repository instead.
- **Security/data/HTTP:** Gitleaks for secret scanning, SOPS + age for encrypted
  files, xh for HTTP requests, and usql for SQL database connections. Installing
  these tools does not create encryption keys or copy credentials.
- **Agent/container development:** Dev Containers CLI (`devcontainer`) is included.
  MCP Inspector is pinned on demand; use it only for the MCP server you intend
  to inspect, and follow the tool's local access instructions.
- **On demand:** Atlas (macOS/Linux), Azure CLI, Google Cloud CLI, AWS CDK/SAM,
  Java/.NET SDKs and MCP Inspector are locked lazy tools. Install one with
  `mise install --locked <tool>`, for example `mise install --locked gcloud`, or
  install the whole catalog with `mise install --locked --include-lazy`.
  AWS SAM is currently macOS/Linux only in mise; native Windows users can use
  AWS's supported SAM installer when their project needs it.
  Lazy tools are excluded from the base doctor's required checks; large SDKs
  may require their documented OS prerequisites and project-specific versions.

**nvm is intentionally replaced by mise's Node version management.** Unix nvm
and nvm-windows are different implementations. Use `mise use node@<version>` in
a project instead of `nvm install/use`; root `.nvmrc` remains a compatibility pin
for existing CI. Remove/disable old nvm, fnm, asdf or Volta shell initialization
if it shadows managed tools. Never silently delete another manager's files.
Do not independently upgrade npm, Corepack shims, or globally npm-install tools
already owned by mise. The npm version comes from the pinned Node release.

### Verify, authenticate and configure

After reopening the shell:

```sh
cd ~/workspace
mise exec -- bun scripts/dev/doctor.ts
mise exec -- bun scripts/dev/doctor.ts --json
# Require a working container runtime and both plugins:
mise exec -- bun scripts/dev/doctor.ts --docker
```

Doctor fails missing/wrong required tool versions and missing Git/npm. Missing
GitHub authentication and Docker runtime/plugins are warnings unless Docker is
explicitly required. `--json` emits structured checks without credential values.
`mise doctor` diagnoses mise itself. Use `where.exe node` / `Get-Command node -All`
on Windows, or `type -a node` on Unix, to find conflicting installations.

Authentication remains per-machine and interactive; never copy tokens into Git:

```sh
gh auth login
gh auth setup-git
gh auth status
vercel login
wrangler login
railway login
```

Only sign into providers the task actually needs. Git identity is personal:
set `git config --global user.name` and `git config --global user.email` after
confirming the desired name/email. Do not guess an email or overwrite an existing
identity. Enable Git LFS hooks when needed with `git lfs install`.

Optional existing workstation/agent settings:

```sh
bun run personal:install
personal workstation doctor
# Only for tasks needing the workspace's managed secrets:
vault login --method=userpass username=crvouga
personal workstation sync
```

The machine bootstrap installs tools/dependencies only. `personal:install` additionally
installs the existing workstation launcher and converges OpenCode configuration;
it may need platform permissions and a Vault login for credential-backed
features. `bun run setup` remains dependency installation only.

### Working with modern repositories

After bootstrap, clone with `gh repo clone owner/repo`, read that repository's
`AGENTS.md`/README and language manifests, and trust its mise config only after
review. Use its lockfile and declared package manager: `bun install --frozen-lockfile`,
`npm ci`, `pnpm install --frozen-lockfile`, `yarn install --immutable`,
`uv sync --locked`, `cargo build --locked` or `go mod download` as appropriate.
Do not install global copies of project-owned TypeScript, ESLint, Prettier, test
frameworks or SDK libraries. For a `.devcontainer` project, use
`devcontainer up --workspace-folder .` after Docker readiness succeeds.

Database servers (PostgreSQL, MySQL, Redis, etc.) and local services belong in
the project's versioned Compose/devcontainer configuration. The shared setup
provides the Docker and SQL clients; it does not start unrequested background
servers or occupy their ports. Python and Bun provide SQLite support without
requiring a separate global database daemon. Mobile/iOS/Android toolchains and
platform-specific native dependencies remain project/OS prerequisites.

Cloud sign-in is per machine: `aws configure sso` / `aws sso login`,
`gcloud auth login` and `az login` only when the task needs that provider.
Use named profiles and existing credentials; never put access keys in this repo.
Kubernetes contexts, cloud resource creation and production deployment still
follow each repository's authorization and IaC rules.

### Containers: CLI versus engine

The manifest installs the **Docker client**. Containers also require a local or
remote Docker engine, Compose v2 and Buildx plugins. These cannot be installed as
one identical unprivileged binary on all OSes.

- **macOS:** run `personal workstation tools docker-setup` to install the pinned,
  checksum-verified Docker Desktop bundle from this repository and open it.
  Complete its first-run agreement/setup in the app. Repeated invocation reuses
  an existing installation. The shared mise Docker client remains in use.
  Vendor installation documentation: Docker Desktop from https://docs.docker.com/desktop/setup/install/mac-install/.
- **Windows:** install/start Docker Desktop from https://docs.docker.com/desktop/setup/install/windows-install/.
  `winget install --exact --id Docker.DockerDesktop` is the package-manager route.
  Enable its WSL2 backend/virtualization prerequisites and finish any reboot.
- **Linux:** follow https://docs.docker.com/engine/install/ for the distribution.
  Install Engine plus `docker-buildx-plugin` and `docker-compose-plugin`, then
  start the daemon (usually `sudo systemctl enable --now docker`). Use Docker's
  documented rootless mode when appropriate. Adding a user to the `docker` group
  grants root-equivalent access; do not do so silently in bootstrap.
- **Remote/headless:** select a preconfigured Docker context instead. Do not
  overwrite an existing context or expose an unauthenticated TCP daemon.

Docker Desktop supplies Compose/Buildx. On Linux they must be installed as CLI
plugins. The pinned mise client should discover plugins in standard Docker
locations; if not, check `docker info` and configure Docker's `cliPluginsExtraDirs`
for that installation. Verify with `docker version`, `docker compose version`,
`docker buildx version`, and optionally `docker run --rm hello-world` (downloads
an image). CLI pinning does not pin or upgrade your engine/plugins.

### Lockfile coverage and reviewed package metadata

Most binary tools have platform URLs/checksums in `mise.lock`; npm/Python tools
also have dependency graphs in `.mise/locks/`. Rust is managed by the native
Rustup backend: mise pins the exact release, and Rustup verifies its versioned
component distribution manifests rather than recording component hashes in mise's
lock. AWS Windows uses the reviewed MSI checksum in the same manifest.

MCP Inspector's dependency graph currently selects the manually published Pino
9.14.0 backport, whose npm publisher metadata differs from the newer 10.x trusted
publisher stream. The manifest's single-version trust-policy exception was added
after verifying npm's SHA-512 integrity and all 139 published JavaScript files
against `pinojs/pino`'s `v9.14.0` tag, plus matching package scripts/dependencies.
The frozen graph still verifies its artifact integrity; no global trust checks
are disabled. Remove that narrow exception when the upstream metadata is fixed.

### Keep machines synchronized

From the checkout, on any platform:

```sh
git pull --ff-only
mise install --locked bun
mise exec --locked bun -- bun scripts/dev/setup.ts
```

For an installed workstation CLI, `personal workstation update` pulls with a clean-tree/fast-forward
guard, refreshes the toolchain/global config and frozen dependencies, and runs the
existing workstation convergence. `personal workstation tools sync` reapplies tool pins/global config
without pulling or touching project dependencies; `personal workstation tools check --json` verifies
them. Sync is explicit; Git commits do not silently update other machines.

For multiple development computers, use [the fleet package](../../packages/fleet/README.md):
`personal fleet-node-add` registers an existing SSH alias in a local roster,
`personal fleet-nodes --onboard` generates per-node connection/auth/editor steps,
and `personal fleet-status --json` diagnoses SSH, authentication, T3 Connect
settings/API and checkout/lockfile drift. `personal fleet-repair --repair workspace`
previews convergence through this same setup script; applying requires
`--apply --yes`. No credentials are copied or cloud resources provisioned;
VS Code/T3 end-to-end tests remain explicit operator steps.

Bootstrap each node once using the same reviewed checkout revision, then check
tool discovery through its actual SSH alias (not just an interactive terminal):

```sh
ssh YOUR_ALIAS 'command -v mise; command -v bun; command -v node; command -v npm'
personal fleet-status --json
personal fleet-repair --repair workspace
personal fleet-repair --repair workspace --apply --yes
```

Review the sync plan before applying. SSH must already work and nodes must be in
your local fleet roster; bootstrap does not create accounts, pair T3, authorize
SSH keys or copy credentials. Remote Bash sessions depend on sshd sourcing
`.bashrc`; shells launched with startup files disabled need an explicit PATH or
the absolute `~/.local/bin/mise exec --locked -- COMMAND` entry point. On Windows,
restart the parent editor/agent process to inherit the updated user PATH.

To change versions: edit pins with `mise use --pin <tool>@<version>` (or edit
`mise.toml`), run `mise lock`, review `mise.toml`, `mise.lock` and any `.mise/locks/`
changes, and test. Keep Bun's pin in `package.json` and the setup action aligned;
keep Node's `.nvmrc` aligned. Run `bun run llms:sync` to regenerate the served
local agent guide, then commit. Do not use `mise upgrade` independently on each machine.
Version policy: use the newest stable compatible releases, with the newest Node
LTS rather than an untested Current release. The current compatibility exceptions
are delta 0.18.2 (newer releases omit Intel macOS), OpenTofu 1.13.0 (all infrastructure
roots and deployment gates require that exact version), and OpenCode 1.19.5
(the workspace's notification/provider plugins still target the 1.x API). Their
major/platform migrations must be validated before moving those pins. Python
and other standalone tools use their latest stable releases at the last update.

Locked downloads still need network access; GitHub limits may require an
authenticated `gh` session. Never disable verification to bypass a failing lock.

### Pinned native T3 for Ubuntu fleet services

The shared setup owner verifies the Linux T3 release archive against the
architecture-specific SHA-256 pins in `mise.toml` (`t3_version` and
`t3_linux_*_sha256`). Artifacts live under `~/.local/share/personal/tools/`.
Workstation uses that absolute executable for policy commands. The worker's
only running T3 is the T3 Code desktop app, installed from the same release's
`.deb` (pinned by `t3_desktop_*_sha256`, computed from the release assets since
upstream `SHA256SUMS` omits packages) and started by the `t3code-desktop.service`
user unit in the GDM auto-login session. It shares `~/.t3` with the former
headless service, so environment identity and pairing are kept. A conflicting
launcher version or a still-running headless service requires reviewed
maintenance; routine fleet-sync never restarts active turns to promote a new
pin. The disposable Ubuntu VM test still exercises the former headless service
and does not cover the desktop session. Private routing and paired execution
require separate evidence.

Normal Ubuntu fleet setup is controller-led:
`npx @crvouga/personal fleet-sync`. See the
[Fleet runbook](../../packages/fleet/docs/ubuntu-sync.md). A controller without
Node/npm must first run this tracked bootstrap (or install the documented Node
prerequisite); `npx` cannot execute before Node/npm exist. Reachable remote targets
are bootstrapped over verified SSH by the same shared owner.

Repeated approved setup reuses an observed matching mise executable and preserves
unchanged managed configuration/lockfile timestamps. It still asks mise and the
frozen dependency owner to inspect actual installations; a previous success marker
is not a reason to skip drift inspection.

### T3 project actions

Project scripts use `bash scripts/dev/project-action.sh ACTION` from the checkout.
Actions are named exactly like the `personal` command they run, so a T3 script
label reads the same as the CLI: `warm`, `portfolio`, `workstation-sync`,
`workstation-update`, `workstation-net-fix`, `workstation-net-check`,
`workstation-net-fix-check`, `fleet-sync`, `fleet-status`, `fleet-repair`, `infra-cliproxy`. Label
each T3 script `Domain: Command words` (`Fleet: Sync`, `Fleet: Status`,
`Workstation: Net check`, `Infra: Cliproxy model health` running `infra-cliproxy model-health`; `infra-cliproxy model-suite --target mock` is the offline, credential-free suite). `fleet-sync` selects the current checkout HEAD as its
exact revision and retains its approval flow; extra arguments such as `--dry-run`
are forwarded. `fleet-status` runs `personal fleet-status --workers`, the
canonical worker audit that reports excluded service hosts. Repair previews without applying. Each invocation runs the shared bootstrap first, reusing installed
locked tools and converging dependencies for the current branch. `warm` performs
only that setup. No global `ws` or `personal` launcher is required. Setup may
install tools on first use; application logins (including Vault for portfolio)
remain per-machine prerequisites. Configuration actions affect the current machine.

### Minimal worker profile

Controller-driven remote bootstrap passes `--worker` to the shared setup owner.
It installs the `vars.worker_tools` subset from `mise.toml`, with versions and
artifacts taken from the same `mise.lock`; native T3 and Ubuntu Docker/service
policy remain source-pinned. `bun scripts/dev/doctor.ts --worker --docker --json`
checks that profile. It does not require unrelated cloud CLIs on workers.
The source-owned `worker-auth.ts` timer renews the worker's existing Vault token
and can restore the declared GitHub account from its authorized Vault service
credential, without copying another machine's login directory.

npx @crvouga/personal fleet-sync

`fleet-node-sync` applies by invocation. It reconciles the locked toolchain, installs

## T3 plan, apply, import and cleanup

```sh
personal t3-apply --dry-run --json
personal t3-apply
personal t3-status
personal t3-cleanup --dry-run
```

Plans show create/update/delete/unchanged/conflict by instance ID, with no settings
values or credentials. `personal t3-apply --plan-hash HASH` binds apply to the exact
settings, ownership state, desired definitions and destination reviewed in a plan.
A stale plan fails. A second apply with identical inputs performs no settings write.

A provider instance becomes managed when created by personal, or explicitly imported:

```sh
personal t3-apply --import personal_codex_proxy
personal t3-apply
```

Import grants ownership of the entire named provider instance. It does not change
its settings immediately. Subsequent applies reconcile that instance to the tracked
definition, including removal of extra fields. Existing unowned instances cause a
conflict, even when their names match. Unrelated instances and settings are preserved.

Removing an instance from the desired definition removes it on the next apply.
`personal t3-cleanup` removes **all owned provider instances** while retaining
threads, projects, pairing, native provider instances, credentials and profile files.
It does not delete T3's data directory or secret store. Historical threads may need
a replacement provider selected after their managed instance is removed.

`--t3-home PATH` selects a T3 base directory (otherwise T3CODE_HOME or ~/.t3).
`--definition FILE` selects a version-1 desired definition. Supported interpolation
is `${workspace}`, `${agents}` and `${node}`. The current schema deliberately supports
the verified Codex proxy adapter fields; it rejects inline credential definitions.
T3 proxy execution requires macOS/Linux/WSL; native Windows execution is unverified.

## State and concurrency

T3 owns `userdata/settings.json`. Personal merges only its declared instances and
stores IDs in `userdata/personal-managed.json`, with mode 0600. Private settings and
state backups sit beside that file. They may contain existing secret references or
values and must never enter Git or reports. Symlink/malformed destinations fail.

Personal operations use an exclusive lock, atomic replacement, pre-write freshness
checks and post-write verification. T3's own theme CLI uses the same optimistic
external-file update pattern; T3 does not honor personal's lock. Avoid concurrent
Settings edits during apply: there is no cross-process atomic compare-and-swap with
T3. No strict transaction across application and ownership files is claimed. Ownership
intent is saved before settings so interrupted creates/removals can be retried.
Inspect interrupted operations before removing a stale `.lock` directory.

T3's installed server source at revision
`322f6544dfad0a3c8a0c8cbecf2c7f7874b14268` was inspected for provider-instance shape,
external settings watch/reload, and optimistic CLI writes. Future T3 schema changes
require adapter verification. A disk-level success is not a live inference test.

The manager needs Node/npm (Node `^22.13.0 || >=23.5.0`), an OpenSSH client,

existing SSH aliases, tests strict SSH access, and offers one enrollment
confirmation for the verified connections. The apply approval binds a fingerprint

out of band before enrolling trust. Unreachable machines remain listed; first
reachability requires an existing trusted LAN SSH route or physical setup of
SSH/Tailscale. No software on the manager can bootstrap a disconnected box.

remaining parity gate. The interactive manager flow can request native sudo authorization over a verified SSH terminal after the consolidated apply confirmation. ## Ubuntu and remote-work safety

The declared common baseline is Ubuntu **26.04 LTS**, amd64/arm64. Other releases
receive `UBUNTU_BASELINE_MISMATCH`; there is no automatic release upgrade or
package downgrade. Workstation audits release, packages, service state and dpkg
consistency, declares snapshot sources for managed transactions, and pins its
selected APT packages. Unrelated applications and package sources are preserved.

Power policy masks sleep/hibernate targets and declares logind sleep/lid defaults.
GNOME lock/idle changes apply to the designated user only. Effective running
session/logind behavior still needs a maintenance/reboot acceptance check; writing
a file does not prove logout/reboot survival. The sudoers fragment is validated
with visudo before installation; this user and its agents can administer the
machine. SSH authentication remains enabled.

SSH forwarding changes validate the complete configuration before reload and
restore the previous fragment on validation failure. Existing listeners,
authentication and firewall rules are preserved. Existing socket activation is preserved for forwarding-only changes; listener
migrations and unmanaged fragments require review. The manager makes a **new**
strict SSH connection after apply. Private-listener/firewall acceptance and
failure-after-reload recovery still require disposable integration testing.

The manager is the only configuration coordinator. No per-node pull timer is
installed. Manager schedule controls use the existing platform adapter:

```sh
personal fleet-sync --schedule status --json

personal fleet-sync --schedule pause --apply --yes
personal fleet-sync --schedule resume --revision FULL_40_CHARACTER_SHA --apply --yes

```

These are manager setup/maintenance operations, not per-node commands. Enable
and resume install the exact published CLI version in the managed manager
runtime and schedule the same whole-fleet command every 30 minutes at the explicit
approved SHA. They refuse dirty artifacts. Pause/disable remove only the manager
schedule. Re-enable with the new approved SHA when promoting a release; the timer
does not resolve `latest`. Linux user scheduling requires lingering; macOS uses
the existing LaunchAgent and requires a user session. Unattended manager boot
acceptance and log-retention configuration remain gates. No node pull scheduler
is installed or necessary.

Routine sync never reboots a box or deliberately kills IDE/T3 work. Explicit
maintenance reboot/reconnect orchestration remains an acceptance gate. Kernel,
driver, firmware, hardware and power failures are outside any “never freezes”
promise. Inspect disk/inodes, swap/memory pressure, `systemctl --failed`, and prior

reboot-on-pressure or kill active work to obtain a green report.

| Muse        | `opencode`    | CLI proxy via OpenCode (`opencode-proxy.ts`)                          |

The CLI proxy multiplexes the provider accounts (fill-first), so every node
shares them. Cursor is not part of the fleet (its backend cannot be proxied).
Native Muse Code is not used: it only talks to Meta's own catalog endpoint, so
Muse models run through OpenCode.

T3 runs Antigravity with its own pinned runtime (the same on every node for the
same T3 release), not the `antigravity` CLI. A managed policy may not hold a
credential, so the instance carries T3's saved-secret marker and each sync
writes the shared proxy key from that node's Vault session into T3's per-host
secret store (`t3:antigravity-key`, `userdata/secrets`, mode 0600);
`GOOGLE_GEMINI_BASE_URL` points it at the proxy. Antigravity sends its catalog
ids (`gemini-3.8-flash`, `gemini-3.1-flash-lite-preview`); the proxy serves
them from the Antigravity account through declared model aliases in
`config.template.yaml`, which every sync applies restart-free (the proxy
hot-reloads its config). Its default Pro model is not served; pick Gemini 3.8
Flash in T3.

The built-in Codex and Claude instances use whatever is first on the PATH T3
inherits from the login shell. Bootstrap keeps the pinned mise shims first
(also at the end of each shell startup file, after nvm or a vendor installer
adds its own directory), so they run the locked versions too.

Each sync checks every agent per node (`agent:<name>:version` against the lock
and `agent:<name>:session`, one tiny prompt through its launcher). Failures do
not stop other workers. New provider settings need a T3 restart: it happens
automatically while T3 is idle, or immediately with `fleet-sync --maintenance`.

Claude’s explicit model is `claude-sonnet-4-6`. Pinned Gemini CLI 0.66.0 supports native
`gateway` authentication with `GOOGLE_GEMINI_BASE_URL` and a runtime Vault key;
its request protocol is Gemini `generateContent`, not OpenAI Responses. Exact models live in `agents/registry.json` and must
be present in the authenticated gateway catalog; no automatic model substitution.

Apply runs bounded authenticated inference plus completed Responses streaming
and a safe echo-tool round trip for each declared provider through the supported
harness route. The echo probe cannot execute shell commands or access files.
These consume small model requests; errors are redacted and do not silently retry
OAuth. Native CLI compatibility and paired T3 execution remain separate gates.
Live five-provider acceptance is still incomplete. `/models` is not proof that five native clients are authenticated.
Do not disguise unsupported native clients with wrapper executables. Missing or
expired unattended Vault authorization remains an explicit dependency; a cached
interactive token is not a supported long-term credential lifecycle.

## Beszel: stock dashboard and history

Beszel supersedes the unshipped Netdata proposal. No Netdata was deployed by this
work. Preserve any independently installed Netdata data and prepare an explicit
migration before removal. The hub is a singleton service, so it runs on the
manager (`definition.json.services.monitoring`) and agents on every worker report
to `https://<manager MagicDNS>:8443`. The manager's uptime is the dashboard's
uptime.

Workstation pins Beszel **0.21.1**: multiarchitecture hub image digest and native
amd64/arm64 archive SHA-256 values are in `monitoring/lock.json`. Compose binds
only loopback port 8090 with persistent `~/Library/Application Support/personal-beszel` on the manager (Docker Desktop). Tailscale Serve
provides private HTTPS port 8443, preserving other handlers and refusing conflicts.
Docker Desktop must be running on the manager (`BESZEL_DOCKER_DESKTOP_REQUIRED`). Existing different hub images require backup and
explicit maintenance instead of an automatic restart during routine sync.

The native Linux agent runs as `beszel`, with persistent `/var/lib/beszel-agent`,
unconditional restart, bounded resource limits and no incoming listener. On macOS
the same pinned binary runs as a root launchd daemon with `KeepAlive`; it is less
sandboxed than the systemd unit and is best effort. It uses authenticated outbound
WebSockets. The selected systemd services are SSH, Tailscale, T3 and manager
sync where present. Journal access and Docker socket access are disabled by
default. Do not expose all host journals or Docker root access merely to get a
collector green. Unavailable service/sensor/GPU/disk-health data is unavailable,
not healthy.

OpenTofu generates the enrollment credential: `BESZEL_FLEET_AUTH` in
`secret/personal/prd` is the password of the normal (non-superuser) Beszel account
`fleet-manager@chrisvouga.dev`. After the vault root has applied, create that
account once on the hub with the generated password (hub superuser → Users →
New record, or the PocketBase API) and grant it the fleet systems.
The hub runs with `SHARE_ALL_SYSTEMS=true`, so systems that account registers are
visible to every hub login. A legacy JSON
`{identity, password}` value is still accepted. No Vault policy is seeded by
setup; never pass the credential on command arguments. Only per-node agent
tokens cross SSH stdin. Supported systems/fingerprints APIs reuse canonical node
records, preserve fingerprints, and reject duplicate names or conflicting hosts.
The account credential remains on the manager. Revoke/rotate it in Beszel and
the existing secret owner; do not erase agent state to force reenrollment.

`fleet-sync --dry-run --json` and `fleet-status --workers --json` report
`dashboardUrl` when the enrolled parent can be resolved. Open that private URL in
a tailnet-connected browser for CPU, memory, disk, network, temperature and
service history of every node. `fleet-status --workers` also verifies the hub
answers privately and that each canonical node is registered, connected and
reporting fresh samples; a manager without a Vault session reports
`beszel:access` as skipped, never as healthy. Fleet reports deployment/readiness;
Beszel reports resource history. Hub outages do not stop SSH/T3 or erase last
working machine configuration, but monitoring stays incomplete.

Supported verification checks authenticated hub version, one canonical record,
connection state, and a one-minute sample received within 180 seconds (with bounded
clock-skew tolerance). Immediately after installation the next sample can be
pending; rerun after its collection interval. Do not count local HTTP health as
historical metrics acceptance.

In the hub UI, configure network monitors with explicit origins: hub→SSH ports,
manager-capable agent→private T3 endpoint, and selected agent→management host
and gateway TCP 443. An unauthenticated gateway `/v1/models` returns 401 and is
not a suitable unauthenticated HTTP success probe. Do not create all-to-all probes.
Network monitor UI configuration, alert thresholds and backup settings are not
reconciled by this implementation. Set sustained CPU/memory pressure, low disk,
offline and available temperature alerts in the stock UI; configure no external
notification destination without authorization. Service failure alert behavior
must be tested for the pinned release before promising it.

Upstream owns tiered metric retention. No arbitrary retention knob or hard disk
quota is invented here. Compose logs are bounded, but data-volume capacity/backup
retention requires an explicit operator setting and acceptance. Use PocketBase’s
supported backup UI/API and approved existing storage, preserving hub identity,
registrations, alert settings and history. Off-host encrypted backup/restore
integration remains an operational gate. The pinned upstream fixture has now
created a backup using `POST /api/backups`, restored it using
`POST /api/backups/{key}/restore`, and verified the original node ID and agent
fingerprint survived while a post-backup record disappeared. This is disposable
API evidence, not an off-host recovery test. See the
[monitoring runbook](../../workstation/monitoring/README.md) for the stock UI procedure. Never edit the live database.

Official feature references: [native agent](https://beszel.dev/guide/agent-installation),
[systemd](https://beszel.dev/guide/systemd), [network monitors](https://beszel.dev/guide/network-monitors),
[REST API](https://beszel.dev/guide/rest-api), and [pinned release](https://github.com/henrygd/beszel/releases/tag/v0.21.1).

## Repeat runs: warm and self-healing

Every step is idempotent, and repeat runs skip work that cannot have changed:

- Ansible playbooks (Ubuntu baseline, Tailscale, T3 desktop, worker recovery,
  Beszel agents and the manager's hub) record a receipt after a successful apply:
  a digest of the playbook sources and variables, never their values, under
  `~/.local/state/personal/fleet/receipts`. A later run with the same digest
  skips the playbook only while a cheap postcondition probe passes (services
  active, hub healthy, agent running).
- Any changed input, failed probe or failed apply runs the playbook in full,
  and a receipt older than 24 hours is ignored, so drift a probe misses still
  heals daily. If a skipped baseline's measured boot or resource policy fails,
  the baseline is reapplied in full in the same run.
- A node whose locked toolchain already passed for the same revision within a
  day skips the toolchain bootstrap (`toolchain-ready`); the manager's run
  checkout does the same (`manager-runs/<sha>.ready`, setup output in
  `<sha>.setup.log`, printed only on failure).
- Provider inference and agent session checks run concurrently, and a pass is
  reused for up to 6 hours while its inputs (node, models, routes, pinned
  versions, verifier and launcher code) are unchanged
  (`receipts/verify/`). Every run still makes one live authenticated gateway
  request with the node's own Vault key; if it fails, everything is verified
  again. Failures and quota-limited results are never cached. T3 links and
  Beszel freshness are always checked live.
- The manager converges alongside the workers (first only with
  `--maintenance`); the canary worker deploys first, then the remaining workers
  concurrently.
- Self-healing: proxy settings the fleet declares are applied restart-free; a
  T3 policy the running app has not loaded is applied by restarting T3 only
  when it has been idle for five minutes (no writes to its state database),
  otherwise it is a non-blocking `T3_POLICY_PENDING_ACTIVE` for the next sync.
- To force a full apply and verification on one machine, delete its receipt
  directory (and `toolchain-ready`).

## Failure, retry and recovery

| Stable outcome                                                                           | Read-only diagnosis and source-owned remedy                                                                                                                                                                              |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `FLEET_MANAGER_ENROLLMENT_REQUIRED`                                                      | Inspect canonical membership and private overrides; rerun interactive enrollment. Preserve conflicting files for review.                                                                                                 |
| `TAILSCALE_ENROLLMENT_REQUIRED` / `TAILSCALE_DEVICE_REPLACED`                            | Verify intended device ID and host fingerprint. Update reviewed private binding only after genuine enrollment.                                                                                                           |
| `TAILSCALE_NODE_OFFLINE` / `TAILSCALE_NODE_MISSING`                                      | Restore power/connectivity or the trusted LAN route; next manager run catches up.                                                                                                                                        |
| `ssh:host-key` / `ssh:auth`                                                              | Verify fingerprint or designated user/public key. Never disable host-key checking or copy another host’s keys.                                                                                                           |
| `SUDO_AUTHORIZATION_REQUIRED`                                                            | Supply initial local privilege through an authorized enrollment step; do not disable SSH authentication.                                                                                                                 |
| `REMOTE_BOOTSTRAP_INCOMPLETE`                                                            | Inspect the named phase, dpkg state, free disk, DNS and package access. Wait for a real package transaction; never delete locks.                                                                                         |
| `TOOLCHAIN_MISE_FAILED` / `TOOLCHAIN_T3_FAILED` / `TOOLCHAIN_FROZEN_DEPENDENCIES_FAILED` | Inspect the nonsecret `toolchain-status.json` under remote Fleet state, available disk and signed artifact/registry access. Rerun the approved revision; never replace pins or bypass checksum/frozen-lock verification. |
| `TOOLCHAIN_CONFIG_CONFLICT` / `TOOLCHAIN_PATH_CONFIGURATION_FAILED`                      | Inspect managed mise ownership and declared shell/PATH settings. Preserve unrelated configuration and resolve the source-owned migration before retrying.                                                                |
| `FLEET_REMOTE_LOCKED`                                                                    | A remote configuration operation still owns the kernel lock. Inspect its PID and state; wait for completion instead of deleting locks or launching another installer.                                                    |
| `FLEET_PROMOTION_BLOCKED`                                                                | Resolve discovery/canary failure before promoting the same revision to remaining nodes.                                                                                                                                  |
| `BESZEL_DUPLICATE_NODE` / host conflict                                                  | Inspect hub registrations. Preserve history/fingerprint and resolve assignment; do not repeatedly create records.                                                                                                        |
| `BESZEL_METRICS_STALE`                                                                   | Check hub/node clocks, connection, capacity and sampling timestamp.                                                                                                                                                      |
| `BESZEL_ENROLLMENT_INCOMPLETE`                                                           | Check hub reachability, account grant and Vault renewal. Raw responses/tokens are withheld.                                                                                                                              |
| `REQUIRED_ACCEPTANCE_UNVERIFIED`                                                         | Run the missing real acceptance check; a skip must never be changed to pass without evidence.                                                                                                                            |

After interruption rerun the same manager command. Manager locks fail closed
rather than stealing a possibly live operation. Inspect active manager and
remote processes before removing an abandoned manager `sync.lock`. Its private
`owner.json` records PID and start time; node `remote-operation.json` records PID,
node and source revision. `toolchain-status.json` records only the shared installer phase and running/failed/passed status, mode 0600; it contains no raw subprocess output. These are diagnostic hints, never proof that a process
has stopped or that a phase succeeded. Remote flock
lives as long as the process tree holds it: a lost SSH connection is not proof that
APT stopped. No installer deletes APT locks or blindly kills package processes.

To roll configuration back, select the previous approved full SHA in the manager
and review/apply it. Dirty deployment directories are never reset. Configuration
rollback is **not** atomic APT rollback, a distribution downgrade, or a restore of
provider OAuth/application databases. Native identities, T3 conversations, worktrees
and uncommitted repositories must be preserved. Test the promised restore path
before replacing a singleton hub or proxy host.

## Agent triage and tracked acceptance issues

Start read-only on the manager:

```sh
personal fleet-sync --dry-run --json --non-interactive
personal fleet-sync --schedule status --json
```

The version 3 report includes a `diagnostics` array per node with stable `code`
and `checkId`, expected/observed evidence, scope, retryability, action-required
state and the owning package's remedy. Measured remote phase durations survive
transport redaction; checks without a measured phase retain null rather than a
fabricated timing. `scope: unverified` means the origin was
not established; a null check duration is unknown, not zero. Node duration is
measured separately. Preflight failures still list every canonical Ubuntu target
with unknown reachability, rather than fabricating offline results or omitting
nodes. Human output includes manager-level failures as well as per-node checks.

Use the repository’s **Developer fleet failure** issue form for a new defect.
For a bug, record package version, approved source SHA, stable check code, whether
this was preview/apply/maintenance, starting condition and the smallest safe
reproduction. Attach only the redacted CLI document after inspecting it. Never
attach `.fleet.local.json`, private SSH config, complete journals, token files,
pairing links or hub backups. A diagnostic owner points to the existing package;
fix persistent policy there, add a regression case, promote one reviewed commit,
and rerun the same manager flow. Do not resolve a failed gate by editing its
reported status or by an untracked remote shell patch.

Open acceptance issues (these do not imply production machines were fault-tested):

- [#209: multi-target SSH bootstrap and interrupted-run recovery](https://github.com/crvouga/personal/issues/209).
- [#210: private paired T3 and five shared-provider routes](https://github.com/crvouga/personal/issues/210).
- [#211: Beszel native lifecycle, private metrics and off-host recovery](https://github.com/crvouga/personal/issues/211).

Each issue has existing evidence and completion criteria. Close a gate only with
the specified real evidence; mocked transport tests cannot substitute for VM or
separate-client acceptance. Newly found defects should have one focused issue with
a reproduction and stable code, linked to the relevant gate.

Canary promotion gates distinguish configuration failure from external acceptance. A failed configuration blocks promotion; missing pairing or monitoring evidence remains an unsuccessful readiness result but does not prevent independent configuration on other enrolled nodes. Native T3 outcomes that need an operator maintenance window (an active listener outside the managed unit, a different running release, a pending policy restart) are reported as failures but likewise do not block other nodes; routine sync never kills active T3 work to clear them. Neither condition advances a fully verified success receipt.

The managed native T3 service uses a stock Tailscale Serve HTTPS route on port
443 to its loopback port 3773. The manager configures and independently reads
back the route without restarting T3. Existing handlers and Funnel exposure are
conflicts requiring reviewed migration; sync never resets Serve. Serve persistence
is independent of application startup, so temporary VPN loss does not become a
T3 startup dependency. The manager then makes a fresh TLS-verified HTTPS
request to the enrolled device. An HTTP 200 proves endpoint transport only; it
does not establish client compatibility, pairing, or model/tool execution.

Boot-policy verification reads the running logind D-Bus properties, sleep target
masks and designated-user lingering. It requires the managed power files to
predate the current kernel boot before recording boot acceptance. Newly staged
policy reports `UBUNTU_MAINTENANCE_REBOOT_PENDING`; routine convergence never
restarts logind or reboots active development sessions.

Remote bootstrap requires at least 2 GiB free and 50,000 free inodes before source
transfer; Workstation then applies its stricter capacity policy. Capacity failures
never delete repositories or caches. Git bundles are bounded to 512 MiB, and a
verified clean cached revision avoids retransferring repository history.

The current-manager provider preflight returned `PROVIDER_UNATTENDED_CREDENTIAL_REQUIRED` for all five providers. It performed no inference or native OAuth login. Restore the existing authorized Vault lifecycle before treating any route as live-accepted.

### Checkout project actions

`bash scripts/dev/project-action.sh fleet-sync` warms the shared toolchain
and passes the current checkout HEAD as the exact revision to the existing approval
flow. Extra arguments such as `--dry-run` are forwarded. The manager can bundle
committed objects from this canonical local repository, including unpublished
commits; dirty working files are never transferred. Review and commit desired
changes before approving deployment. The Ubuntu baseline now owns the native
Docker engine, Compose and Buildx on every enrolled Linux workstation, preserving
third-party engine ownership conflicts and existing running workloads. Workstation
launcher/link convergence is part of the node apply, with credentials still checked
separately. A dependency receipt proves frozen installation inputs only.
