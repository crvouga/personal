# Zoomies

Self-hosted GitHub Actions runner controller ([zoomies.sh](https://zoomies.sh)) at https://zoomies.chrisvouga.dev. One controller; hosts (home machines, rented VMs) join it with single-use tokens, and pools turn them into ephemeral runners that workflows select with `runs-on: zoomies-ubuntu-2404`.

Everything here is declared in the repository. Hosting, volume, DNS/TLS and secrets are OpenTofu; the image is built and deployed by the [Deploy](../../.github/workflows/deploy.yml) workflow; the controller's own application data (GitHub App connection, pools, join tokens) is applied through its API by `src/configure.ts` and `src/join-token.ts`.

| Concern             | Where it is declared                                                                                                                                                                                                 |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Service, port, env  | `zoomies` entry in the [inventory](../infra/tofu/modules/inventory/inventory.tf.json) (`services` root creates the Railway service, custom domain, DNS CNAME + TXT; Railway issues TLS for `zoomies.chrisvouga.dev`) |
| SQLite persistence  | Railway volume `zoomies-data` mounted at `/data` (`ZOOMIES_STATE_DIR`, `ZOOMIES_DB_PATH`); one replica, no sleep                                                                                                     |
| Backups             | Zoomies' built-in nightly backup to `zoomies/production` in the shared R2 bucket, sealed with `ZOOMIES_BACKUP_PASSPHRASE`, last 14 kept                                                                              |
| Secrets             | OpenBao `secret/personal/prd`, written by the `vault` root and injected into Railway by the `services` root                                                                                                          |
| Image               | [Dockerfile](Dockerfile): official `ghcr.io/eyupio/zoomies` pinned by release and digest, plus a static shell for the credential-file entrypoint                                                                     |
| Webhooks vs polling | `ZOOMIES_EXTERNAL_URL` makes GitHub deliver to `/webhooks/github`; Zoomies' default `ZOOMIES_POLL_FALLBACK=true` keeps polling as the fallback with no extra configuration                                           |

## Secrets

| Vault key (`prd`)                                                              | Source                                                                     |
| ------------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| `ZOOMIES_ENCRYPTION_KEY`                                                       | Generated once by the `vault` root (32 random bytes, `prevent_destroy`)    |
| `ZOOMIES_BOOTSTRAP_TOKEN`                                                      | Generated by the `vault` root; creates the first (`platform`) API identity |
| `ZOOMIES_BACKUP_PASSPHRASE`                                                    | Generated by the `vault` root                                              |
| `ZOOMIES_GITHUB_APP_ID`, `_INSTALLATION_ID`, `_PRIVATE_KEY`, `_WEBHOOK_SECRET` | Supplied by you through `bun run vault:edit` after creating the App        |

The bootstrap token is the controller's automation identity: it is written to a `0400` file at start, registered as an API token on an empty database, and is what the scripts here authenticate with. It cannot sign in to the UI. Create people accounts with it after the first deploy (below). Zoomies logs `bootstrap.ignored` on later starts; that is expected.

## First deployment

After the PR is merged to `main`, [Deploy](../../.github/workflows/deploy.yml) runs automatically (changes under `packages/infra/` and `packages/zoomies/`). In order it applies `foundation`, `bootstrap`, `vault` (generates the secrets), builds and pushes `ghcr.io/crvouga/chrisvouga-zoomies`, applies `services` (Railway service, volume, domain, DNS), verifies the rollout and probes `https://zoomies.chrisvouga.dev/healthz`.

Run it manually, or re-run after a failure:

```bash
gh workflow run deploy.yml --ref main -f action=deploy -f service_id=zoomies
bun run gh:deploy:status
```

Check the result with `bun run health --only services` and `curl -s https://zoomies.chrisvouga.dev/readyz` (`bootstrap_required` must be `false`).

## Connect GitHub (once)

GitHub does not allow an App to be created through an API or OpenTofu, so this is the one step that needs your hands. It is codified here so it is repeatable:

1. Create a GitHub App owned by `crvouga` with webhook URL `https://zoomies.chrisvouga.dev/webhooks/github`, a webhook secret you generate, events `workflow_job` and `issue_comment`, and repository permissions Administration (write), Actions (write), Checks (read), Statuses (read), Metadata (read). (**Installations → Connect GitHub** in the UI does the same through GitHub's manifest flow, but then the credentials live only in the Zoomies database.)
2. Install it on `crvouga/personal` (or other repositories). The installation id is the number in `https://github.com/settings/installations/<id>`.
3. Store the values in Vault:

   ```bash
   bun run vault:edit   # set ZOOMIES_GITHUB_APP_ID, ZOOMIES_GITHUB_APP_INSTALLATION_ID, ZOOMIES_GITHUB_APP_PRIVATE_KEY, ZOOMIES_GITHUB_APP_WEBHOOK_SECRET
   ```

   The prompt is single-line: enter the private key PEM with each newline written as `\n`; `configure` restores them.

4. Apply them to the controller. The Deploy workflow does this after every Zoomies rollout; to do it now:

   ```bash
   bun run zoomies:configure
   ```

`configure` is idempotent: it waits until the controller is up and claimed, connects the installation only if absent (target defaults to `crvouga/personal`; override with `ZOOMIES_GITHUB_TARGET` / `ZOOMIES_GITHUB_TARGET_TYPE`), and creates the pools declared in [`src/spec.ts`](src/spec.ts) only if missing. It never edits an existing pool, so capacity, labels and sizes tuned in the UI persist. Without the App values it exits cleanly and says what is missing.

## Add a host

Any Linux machine with Docker or Podman works: home hardware or a rented VM. It connects outbound, so no inbound port is needed.

```bash
bun run zoomies:join-token --capacity 4 --label site=home
```

Run the printed command on the new machine. The token is single use, expires in 15 minutes (`--ttl 1h` to change), and is shown only once. Repeat for each host; the pool above schedules onto all of them. Hosts upgrade separately from the controller (see Upgrades).

Use the pool in a workflow:

```yaml
jobs:
  build:
    runs-on: zoomies-ubuntu-2404
```

Only trusted repositories should use self-hosted runners; read the [Zoomies security guidance](https://zoomies.sh/security/) before enabling pull requests from forks.

## Upgrades and rollback

Change the release tag and digest in [`Dockerfile`](Dockerfile) in a pull request. Merging builds a new image and Deploy rolls it out; the volume keeps the database. Zoomies applies schema migrations on startup, so check upstream release notes before an older tag is selected. Agents on hosts are upgraded separately by Zoomies.

To roll back to a previously published image:

```bash
gh workflow run deploy.yml --ref main -f action=deploy -f service_id=zoomies -f image_tag=<previous commit sha>
```

## Not automated

- Creating the GitHub App itself (above).
- Restoring from a backup. Backups are written automatically and listed under **Settings → Backups**; use upstream's [`zoomies restore`](https://zoomies.sh/backup-and-restore/) procedure with `ZOOMIES_ENCRYPTION_KEY` from Vault and the passphrase from `ZOOMIES_BACKUP_PASSPHRASE`.
- Provisioning rented cloud machines. Create the VM by whatever means you use (it is outside this repository), then add it as a host as above.
- Creating UI accounts for people. The bootstrap token is a `platform` token: `zoomies users create --username <name> --role admin --password <password>` with `ZOOMIES_URL` and `ZOOMIES_TOKEN` (the bootstrap token) set, or the API.
