OS-level configuration for machines we operate (NixOS roles, hardware profiles, bootstrap, sync). Does not create cloud resources or DNS; that's `../infra`.

Git is the only control surface after bootstrap. After that, SSH is read-only emergency access for fleet system configuration. The devbox dev account may write project files and install user tools over SSH; system configuration still changes only through Git. `just status NODE` only reads. The installer USB is the one-time install write, and it wipes the internal disk.

After the first bootstrap, the only manual tasks are physical: hardware replacement, cleaning, and one-time BIOS setup. Anything else that seems to need a person at the machine is a bug in the automation. Fix it in this package.

`modules/base.nix` is the only module shared by every role: users, SSH, the sops age-key path, store maintenance, the watchdog, boot fallback, the disk alert, the shared disk layout, pull sync, boot identity, the revision endpoint, and drift. Do not put role switches in `base.nix`. `hosts/` composes a role plus capability modules. It never names a machine.

Roles:

- `ci`: `hosts/ci.nix`, `fleet.nix`, `modules/ci-runner.nix`. The GitHub App key, runner users, slot cache, and `secrets/fleet.yaml` stay here. CI runs untrusted pull-request code.
- `web`: `hosts/web.nix`, `web.nix`, `modules/web-server.nix`. Apps are OCI images behind Caddy, with `secrets/web.yaml`.
- `cache`: `hosts/cache.nix`, `cache.nix`, `modules/cache-server.nix`. This is the attic binary cache. It is not the optional CI scratch substituter in `modules/cache.nix`.
- `devbox`: `hosts/devbox.nix`, `devbox.nix`, `modules/devbox.nix`. SSH user `dev`, home `/nix/devbox`, no sudo, no CI runner units or credentials. The installer requires a public key before wiping; it is kept root-owned at `/nix/fleet-state/devbox/authorized_keys`. Runtime project work over SSH is allowed; role and system configuration stay Git-managed.
- `netboot`: `hosts/netboot.nix`, `netboot.nix`, `modules/netboot.nix`. Firmware tries the network first. Pixiecore asks `fleet-netboot-policy`, which tells the client to boot the local disk unless `reinstall.nodes` or `reinstall.roles` in `settings/shared.nix` flags it. The host does not serve an installer that can finish an install, so a flag does not install a node. `dhcpNoBind` stays true unless this host is the DHCP server for that network.

CI and web must never share an age key or a secrets file. Cache, netboot and devbox use their own keys and files too. `fleet-install` refuses two role keys on the `FLEET-KEY` volume with the same age recipient, even when their comments differ. It validates a private snapshot of a supplied key before partitioning and verifies the installed copy.

To add a role, add `modules/<role>.nix` with only that role's services, add `hosts/<role>.nix` that imports `base.nix` and that module, and add a settings file plus a `nixosSystem` in `flake.nix`. Set `reboot.drainCommand` only when the role must drain before a kernel reboot. Every role uses `modules/disks/internal.nix`.

To add a machine of an existing role, download `scripts/fleet-node.sh` onto that machine and run it. It is one file. It does not need Nix, a git checkout, `just`, or a second computer. The person types `ci`, `web`, `cache`, `netboot`, or `devbox`, or passes it with `--yes` (`bash fleet-node.sh ci --yes`, or `FLEET_YES=1`) to run with no typing at all; `--yes` takes the confirmation line as typed and every disk refusal below still applies. The program names that role and the internal disk, and it erases nothing until that line is typed back. A USB, removable, hotplug, or ambiguous disk is refused on Windows, macOS, and Linux. A mounted internal disk is not refused: the disk holding the running system is always mounted, and converting a running machine is the point. The installed hostname stays `<role>[-gpu][-highmem]-<4 hex>` from the hardware id. Do not add a host file, a profile, or a hand-picked name. A machine with no OS cannot download; `bash fleet-node.sh flash` writes the same installer to a USB disk and refuses an internal disk. Removing a node is `fleet-remove` on that node: it withdraws the runner, writes `/nix/fleet-state/withdrawn` (runner units refuse to start while it exists, even after a reboot), and powers the machine off by itself when no job is running. Reinstalling wipes the marker.

An agent can do all of that for the person. Tell it: `Set this machine up as a fleet <role> node by following https://raw.githubusercontent.com/crvouga/workspace/main/packages/fleet/docs/agent-install.md` (`just enroll <role>` prints that sentence with a token in it). The same runbook is inside the downloaded file as `bash fleet-node.sh guide`, which needs no Python. The agent runs `sudo bash fleet-node.sh doctor <role> --json`, which writes nothing, reports every problem at once, and names the exact disk (`erases`). It shows the person the role and that disk, gets an explicit yes, and only then runs `--yes`. `--yes` is never the person's approval. The install runs the same checks first, before any prompt, and refuses on any `FAIL`: not root, not x86_64, not UEFI, no boot tool, an unusable staging filesystem, an unreachable release, too little disk space, and an enrollment token that is spent, expired, or made for another role (checked with Vault's `sys/wrapping/lookup`, which does not spend it). A missing token is a `WARN`, because a node that generates its own key cannot decrypt what the others share. Every run writes a timestamped log with secrets redacted (`<state>/logs/fleet-node-*.log`, newest 20 kept, mode 0600) and prints its path with every failure, along with one `Why:` line and exactly one `Next:` line. Exit 0 is done, 2 is a refused precondition with nothing written, 70 is a bug in the program. The installer keeps its own step log and copies it to `/nix/fleet-state/logs/install.log` on the new node; a failed step prints `FLEET-FAIL` with the line and the log path. On the node, `fleet-node status` is the read-only answer to whether it came up: role, hostname, revision, sync timer, failed units, and the last rolled-back switch. Do not add a collector, a callback to a server, or a second way to approve a wipe.

## The installer wizard

For a person, not an agent: go to the `fleet-installer` GitHub release, download the file for the computer in front of you, open it, and answer the questions. It runs on Windows (x64), macOS (Apple silicon and Intel), and Linux (x64 and arm64). It is a local web page opened in the browser: `packages/fleet/wizard/` (Python, packaged per OS by `wizard/build.py` with PyInstaller). [docs/installer.md](docs/installer.md) is the user guide. The wizard does two things. It makes an install USB for another computer from any OS, and on x86_64 Linux it converts the running machine in place (`kexec`, the same path as `fleet-node.sh`). Windows and macOS cannot restart into the installer, so the wizard says so and makes the USB. An existing fleet node converts with `fleet-node <role>`, because a PyInstaller binary does not run on NixOS without `nix-ld`.

The web server normally runs without administrator rights and listens on 127.0.0.1 only. Every API request needs this run's secret and a loopback `Host` header. The static page contains no secret or machine facts; the tab retains its API token in sessionStorage so Reload works without putting the token back in the URL. The disk work is `wizard/helper.py`, started through the OS's own prompt (UAC, the macOS password dialog, polkit) with a request file. The helper trusts nothing in it: it re-lists the disks, re-hashes the image, and refuses anything that is not exactly the disk that was planned. The wizard downloads and writes in pure Python (`urllib`, a raw-device write with read-back verification), because Windows has no `dd` or `curl` guarantee. A USB is reported ready only if the read-back hash equals the verified image. Failed writes can leave a USB incomplete; retry the full write. Device leases exclude other wizard helpers; confirmations expire after 15 minutes and are single-use. Terminal state and its result are published atomically.

Use `decide.invariant(condition, what, fix, **context)` for every fact the code relies on, never a bare `assert` (`python -O` removes those). An invariant names the broken thing, carries the values that make it diagnosable, and says what to do. It is raised, never swallowed; `main()` stops with exit code 71, and the wizard shows it in the job result. State markers (`installed`, `withdrawn`) are validated on every read, so a corrupt one stops the program instead of being guessed at. Assert at the point of use as well as at the point of decision: the helper repeats the checks the server made. Do not add a test seam that can reach a real disk: `FLEET_WRITE_TARGET` is honored only together with `FLEET_DISKS_FILE`.

Every build must pass its own `--selftest` (page bundled, server up, authentication enforced, helper relaunch, write and read back) before CI publishes it, on every platform in the `wizard` job of `workflows/fleet.yml`. `wizard/ui-e2e.cjs` clicks through the real page in Chromium on every platform. The macOS and Windows downloads are unsigned: say so in the user guide, do not hide it. Known gaps, so nobody assumes otherwise: an install USB cannot carry a role or an enrollment token (the UEFI menu waits for a deliberate role choice, and a node made this way generates its own age key); the elevation prompts (UAC, macOS dialog, polkit) have unit tests for the commands they run but are not clicked through in CI. Devbox USB installs ask for a public key on the console or read devbox.pub from FLEET-KEY. Converting an existing CI node refuses active jobs, withdraws the idle runner through its existing credential and closes its job admission gate before reboot. A failed handoff leaves a withdrawn node that can be reinstalled, including back to CI.

## Cattle, not pets

Any node is replaceable by any other box with the same role and capabilities. Configurations exist only per role (`ci`, `web`, `cache`, `netboot`, `devbox`), optionally combined with a capability that changes the software (`hosts/ci-gpu.nix`). `hosts/` filenames must be the role plus capabilities from that set.

Never add per-machine configuration or a hand-picked name. No `hardware-configuration.nix`, no disk serial, no `/dev/sdX` or `/dev/nvmeN`, no interface name, no MAC, and no static `networking.hostName`. If a machine seems to need special treatment, add a capability module or fix `modules/hardware/generic.nix`. `scripts/cattle.py check` and `nix flake check` fail the build when those show up in a Nix file.

The generic profile boots a reasonable x86_64 UEFI machine: broad initrd modules, both Intel and AMD microcode, redistributable firmware, and DHCP on every wired Ethernet device by type. aarch64 is a later architecture variant of these same roles, not a board file. The kernel is the NixOS default.

Disko installs the sentinel `/dev/fleet-install-disk`. The installer requires exactly one internal disk, skipping USB, removable, hotplug, and anything mounted; multiple eligible disks are refused. With `FLEET_AUTO=1` it wipes that disk. A manual `fleet-install ROLE` still requires the path to be typed. Filesystems are labeled `SHBOOT` and `sh-nix` and mounted by label.

### Hostnames

A hostname is `<role>[-gpu][-highmem]-<4 hex>` and is set at boot, not in the Nix config. Examples: `ci-a3f9`, `ci-gpu-7c21`, `ci-highmem-02be`, `ci-gpu-highmem-7c21`, `web-a3f9`. The id is the first 4 hex digits of sha256 of the DMI system UUID, or of the lowest permanent MAC when the UUID is missing. Four digits can collide; the UUID makes that unlikely, and a reinstall of the same box keeps the name. The transient name is applied before SSH, metrics, and runner registration. `/etc/hostname` stays absent. The installer image has no fleet hostname.

GPU is a software capability: `environment.etc."fleet/capabilities.d/gpu"` exists only in the `ci-gpu` closure. high-mem is not a closure. It is MemTotal strictly above `capacity.highMemGiB` (60) times 1024, so a 64 GiB box qualifies and a 32 GiB box does not. The hostname tag is `highmem`. The runner label is `high-mem`.

To add a capability that changes software, add `modules/capabilities/<name>.nix`, import it from `hosts/<role>-<name>.nix`, and allow that extra stem in `HOST_CAPABILITIES` inside `scripts/cattle.py`. Write one tag per line under `environment.etc."fleet/capabilities.d/<name>"` and list it in `TAG_ORDER` when the hostname should include it. A legacy GPU driver is another module, still not a machine. A fact that does not change the closure, such as high-mem, is a threshold in `capacity` and is not a host file.

### Capacity and labels

CI runner count is computed at boot in `scripts/cattle.py`, from `settings/shared.nix` `capacity`: `min(slotMax, max(1, min(cores / perRunnerCores, (MemTotal MiB - reserveGiB * 1024) / (perRunnerGiB * 1024))))` with integer division. Production constants are 4 GiB reserved, 6 GiB and 2 cores per runner, and at most 8. A 16-core 32 GiB machine stays at 4 slots. The closure contains units `slot-1` through `slotMax`; only the live count is started. Workflows target `self-hosted`, `nixos`, and `ci`, plus `gpu` or `high-mem` when they need that capability. They do not target a machine or a model name. `nix build .#nixosConfigurations.ci-gpu` is opt-in. The default CI build does not download the unfree driver.

`http://127.0.0.1:9101/metrics` reports `nixos_node_info` with hostname, role, capabilities, and revision, plus `fleet_sync_rollback` and `fleet_disk_used_percent` when a disk sample exists. It is localhost only. `fleet-drift` compares `/etc/fleet/revision` with `origin/main` and fails when main is older than `drift.maxMinutes` (30) and this node is not on that commit. A newer merge stays in grace. `unknown` fails the unit. The timer stays off while `repo.url` contains `TODO`. A down node cannot report its own silence. `fleet-disk` fails when `/nix` or `/boot` reaches `disk.alertPercent` (90). TODO: nothing scrapes the metrics port, and `monitoring.pushUrl` is not read, so that silence is invisible outside the machine. Do not invent a collector. This is not OpenTofu plan drift.

To add an app on the web role, append one attrset to `apps` in `web.nix`: `name`, `domain`, `port`, `containerPort`, and `image` (the OCI image CI already publishes). Set `envSecret` only together with this role's encrypted `secrets/web.yaml`. A null `image` is the local placeholder used until those values are real. Do not invent a domain or an image tag.

## Bootstrap

The installer ISO is built by the `Fleet` workflow. The workflow uploads `fleet-installer` as an Actions artifact that expires after 14 days, and on merge it also publishes that ISO, its sha256, and `fleet-node.sh` to the `fleet-installer` GitHub release. The release is the copy a new machine downloads. `scripts/fleet-node.sh` is one file: it fetches that release, asks for `ci`, `web`, `cache`, `netboot`, or `devbox`, names the internal disk, and reboots into the installer only after that line is confirmed. It does not need Nix, `gh`, or a checkout. If the download is missing or expired, it exits non-zero, writes nothing, and prints one next step. A second fetch of the same release asset is the same bytes. `ci-gpu` is not on the image. The boot menu lists the five roles. The UEFI boot menu waits for a deliberate choice, and labels every role as erasing the internal disk. `fleet.role=` on the kernel command line selects the closure. A later `fleet.role=` wins, which is how the web, cache, and netboot menu entries override the default. The live image then runs `fleet-auto` and wipes the chosen internal disk. `sshKeys` may stay empty. `just bootstrap ROLE IP` only forwards a keyboard over SSH when a key is configured, and it sets `FLEET_AUTO=1`. It does not build Nix and it does not read an age key. `just fetch-iso` is the legacy 14-day artifact download. Do not use it to add a node.

The private key is created at `/nix/fleet-state/secrets/age.key`. The public key is printed on the console and stored in `age.pub`. A filesystem labeled `FLEET-KEY` supplies `<role>.age` when the file is already there, and receives a newly generated key when it is not, so the next node of that role can decrypt the same sops file. This package does not generate a key into git. `--token-file PATH` (or `FLEET_ENROLL_TOKEN`) replaces the `FLEET-KEY` USB: the token is a single-use Vault response-wrapping token that holds the role key at `secret/data/fleet/<role>`, field `age_key`. Run `just fleet-keys` once to create the missing role keys (private keys to the vault root's git-ignored `fleet-age-keys.auto.tfvars.json`, public recipients to `.sops.yaml`). Then `just enroll <role>` prints the one line to paste on a new node: it downloads `fleet-node.sh` and runs it with `FLEET_ENROLL_TOKEN` set. It goes onto the installer command line as `fleet.enroll=`, is unwrapped by `fleet-install` before the disk is touched, and is never printed. A refused or spent token wipes nothing. A token is never an argument (`--token VALUE` is refused). The `FLEET-KEY` volume still wins when it holds `<role>.age`. The path is owned by the vault OpenTofu root (`vault_kv_secret_v2.fleet`, input `fleet_age_keys`, a complete map of role to `AGE-SECRET-KEY-` value, each distinct). Change it there with a reviewed plan, never with `bao kv put`. Declaring it is not applying it. The netboot ramdisk does not carry the role closures. TODO: the netboot host does not serve this ISO, so a `reinstall.nodes` or `reinstall.roles` flag does not install a node. Reinstall with `fleet-node.sh` on the machine.

The ISO host key is ephemeral. The installed host key is `/nix/fleet-state/ssh/ssh_host_ed25519_key`, generated on the machine. The console prints its fingerprint after reboot. Steps that stay physical are in `docs/checklist.md`.

To rotate a role age key, follow `secrets/README.md`. The new private key is encrypted to the current key as the sops secret `age-key-next`. Set `rotateAgeKey = true` on that role in the same commit. The node installs it to `/nix/fleet-state/secrets/age.key` when it pulls. A second commit drops the old recipient. Do not SSH the key onto the node. `ci-gpu` uses the `ci` key. This package does not generate keys into git.

To reinstall a node, run `fleet-node.sh` on that machine. A `reinstall.nodes` or `reinstall.roles` flag does not install a node, because the netboot host does not serve an installer that can finish. TODO: no smart PDU model is selected and this repo does not power-cycle a node. A power cycle is physical until that integration exists. Do not invent a vendor, a host, or a credential.

## Sync and rollback

comin is not in nixpkgs at the pinned revision `7c8764b7`, and this flake does not add an unlocked input. `modules/sync.nix` and `scripts/fleet-sync.sh` are the pull agent. Do not also enable `system.autoUpgrade`.

Every role polls `main` over HTTPS. There is no `deploy` branch and no `canary` branch. The timer stays off while `repo.url` contains `TODO`. The poll is 300 seconds plus 30 seconds of jitter. The node runs `nix build --max-jobs 0` and switches only when that role's toplevel is already in the binary cache. A miss exits and the timer retries. The node does not build locally. While `binaryCache.url` is empty or contains `TODO`, it waits the same way. `self.rev` is null on a dirty tree. `system.configurationRevision` is `self.rev`, or `unknown`. It is published at `/etc/fleet/revision` and `http://127.0.0.1:9101/metrics` (localhost only).

A kernel, initrd, or module change drains first, then sleeps for `cksum(stable id) % delayMaxSeconds` (default 7200; 0 disables), then reboots. The id is read before the drain. If that read fails, the node does not drain and does not reboot. On CI the drain command is `fleet-drain`. A failed drain does not switch or reboot. Other changes switch in place and do not drain. After every switch, including the bootloader update before a reboot, the node checks that it can reach GitHub and the binary cache and that `fleet-sync.service` still loads and `fleet-sync.timer` is not failed. A failure writes `/run/fleet/health-failure`, restores the previous generation, does not reboot, and the unit exits non-zero. The timer retries. TODO: that failure is local until a collector exists.

systemd-boot keeps `bootGenerationLimit` generations (8). The menu waits 5 seconds. `scripts/boot-count.sh` marks only the newest entry with `bootTries` (3) tries. This nixpkgs pin has no boot-counting option. `boot.loader.systemd-boot.graceful` is not fallback. `systemd-bless-boot` clears the count after userspace starts. A generation that never gets there falls through to the previous entry. The hardware watchdog is `RuntimeWatchdogSec=30s` and `RebootWatchdogSec=5min`, so a hung userspace reboots. Weekly `nix.gc` deletes store paths older than 14 days. The journal is volatile and capped at 256M because the root is tmpfs. `fleet-disk` is the fullness alert.

Git read access is `repo.auth`: `none`, `ssh` (`/run/secrets/git-read-key`), or `token` (`/run/secrets/git-read-token`). Encrypt that credential separately into each role's sops file. Any auth other than `none` requires that role's `secretsFile`.

The fleet binary cache is attic. Clients add it as a substituter only when `binaryCache.url` and `binaryCache.publicKey` are both set and neither contains `TODO`. Leave both null until they are real. Do not enable it together with `cache.remote`. Attic storage is bind-mounted from `/nix/fleet-state/attic` because the root is tmpfs. The cache role stays off while its `secretsFile` is null, so a build does not mint a JWT.

`.github/workflows/fleet.yml` is a byte copy of `workflows/fleet.yml`. It runs on `ubuntu-latest`, never on this fleet, so a broken fleet can still be fixed by merging. It has no `on.paths` filter. The `Fleet` job always reports a status. When the diff does not touch this package, that job succeeds without building. A pull request that does touch it runs `nix flake check --max-jobs 2` (cattle enforcement and the NixOS VM tests, including `follow-up`) and builds `ci`, `web`, `cache`, `netboot`, `devbox`, and the installer. The job cap keeps the QEMU guests inside the 16 GB GitHub-hosted runner. `follow-up` is the check that a node which has switched can pull and switch to the next commit, and that a failed health check restores the previous one. It is required because `nix flake check` runs it. There is no separate GitHub status name. `ci-gpu` is evaluated and is not a default build.

The merge queue runs the same check, then pushes those five toplevels to attic. The push fails closed while `FLEET_CACHE_URL`, `FLEET_CACHE_NAME`, or `FLEET_ATTIC_TOKEN` is unset. Do not invent them. There is no post-merge cache job. The ruleset's merge method is `MERGE`, so the merge-group commit is the commit that lands on `main`, and `configurationRevision` matches the cached system. Squash or rebase would not.

A rollback is a revert pull request through the same checks and the same queue. The previous commit's systems are already in the cache. systemd-boot keeps `bootGenerationLimit` generations (8), selectable from the console. There is no force-push rollback.

`main` requires a pull request, the `Required` and `Fleet` checks, and the merge queue. Direct pushes and force pushes are refused. That ruleset is OpenTofu in `packages/infra` (`inventory.tf.json` and `foundation/repository.tf`). Declaring it is not applying it. Apply a reviewed plan. Do not apply it from this package.

One path changes a node. Open a pull request, let `Required` and `Fleet` pass on GitHub-hosted runners, and let the merge queue land it on `main`. Nodes pull that commit. Do not push `main` directly, force-push it, or change a node by hand.

`.github/workflows/flake-update.yml` is a byte copy of `workflows/flake-update.yml`. Once a week it runs `nix flake update` in this package and opens or updates one pull request on `chore/fleet-flake-lock`. That pull request uses the same checks and the same queue. It does not push `main`.

This package does not own GitHub configuration, buckets, billing, DNS, or other workspace infrastructure. Every dependency is pinned in `flake.lock`. Do not update it implicitly. Do not commit tokens, age private keys, or plaintext secrets.

Run `bun run --filter @pkgs/fleet check` for portable checks. From this package: `just check`, `build-node`, `build-web`, `build-cache`, `build-netboot`, `build-iso`, `vm-test`, `fetch-iso`, `flash-usb ISO DEVICE`, `bootstrap ROLE IP`, and `status NODE`. `fetch-iso` and `flash-usb` do not need Nix. `bootstrap` does not build.

`flash-usb` and `bootstrap` are destructive. Obtain explicit human approval identifying the disk before executing them. An interactive confirmation is an additional check, never authorization. Do not execute a generated installer or a VM against physical disks. Never print secrets, place them in CLI arguments, or copy plaintext credentials into the Nix store. Never change GitHub settings, secrets, or billing without explicit approval. Runtime registration uses the configured GitHub App; tokens remain in `/run`.

CI nodes drain through `scripts/drain.sh` (`fleet-drain`) before a kernel reboot. Restrict runner projects to private trusted code, require `nixos` and `ci` routing labels, and never run fork PRs or `pull_request_target` on the runner fleet. Keep credentials root-only. Inspect actual upstream module source at the locked nixpkgs revision when changing module behavior. A local portable check is not `nix flake check` and is not a VM test. Report when those were not run.
