OS-level configuration for machines we operate (NixOS roles, hardware profiles, bootstrap, sync). Does not create cloud resources or DNS; that's `../infra`.

Git is the only control surface after bootstrap. After that, SSH is read-only emergency access for fleet system configuration. The devbox dev account may write project files and install user tools over SSH; system configuration still changes only through Git. `just status NODE` only reads. The installer USB is the one-time install write, and it wipes the internal disk.

After the first bootstrap, the only manual tasks are physical: hardware replacement, cleaning, and one-time BIOS setup. Anything else that seems to need a person at the machine is a bug in the automation. Fix it in this package.

`modules/base.nix` is the only module shared by every role: users, SSH, the sops age-key path, store maintenance, the watchdog, boot fallback, the disk alert, the shared disk layout, pull sync, boot identity, the revision endpoint, and drift. Do not put role switches in `base.nix`. `hosts/` composes a role plus capability modules. It never names a machine.

Roles:

- `ci`: `hosts/ci.nix`, `fleet.nix`, `modules/ci-runner.nix`. The GitHub App key, runner users, slot cache, and `secrets/fleet.yaml` stay here. CI runs untrusted pull-request code.
- `web`: `hosts/web.nix`, `web.nix`, `modules/web-server.nix`. Apps are OCI images behind Caddy, with `secrets/web.yaml`.
- `cache`: `hosts/cache.nix`, `cache.nix`, `modules/cache-server.nix`. This is the attic binary cache. It is not the optional CI scratch substituter in `modules/cache.nix`.
- `devbox`: `hosts/devbox.nix`, `devbox.nix`, `modules/devbox.nix`. SSH user `dev`, home `/nix/devbox`, no sudo, no CI runner units or credentials. The installer requires a public key before wiping; it is kept root-owned at `/nix/fleet-state/devbox/authorized_keys`. Runtime project work over SSH is allowed; role and system configuration stay Git-managed.
- `netboot`: `hosts/netboot.nix`, `netboot.nix`, `modules/netboot.nix`. Firmware tries the network first. Pixiecore asks `fleet-netboot-policy`, which tells the client to boot the local disk unless `reinstall.nodes` or `reinstall.roles` in `settings/shared.nix` flags it. The host does not serve an installer that can finish an install, so a flag does not install a node. `dhcpNoBind` stays true unless this host is the DHCP server for that network.

CI and web must never share an age key or a secrets file. Cache, netboot and devbox use their own keys and files too. `fleet-install` refuses two role keys on the `FLEET-KEY` volume with the same age recipient, even when their comments differ. It validates a private snapshot of a supplied key before partitioning and verifies the installed copy.

To add a role, add `modules/<role>.nix` with only that role's services, add `hosts/<role>.nix` that imports `base.nix` and that module, and add a settings file plus a `nixosSystem` in `flake.nix`. Set `reboot.drainCommand` only when the role must drain before a kernel reboot. Every role uses `modules/disks/internal.nix`.

To add a machine of an existing role, download `scripts/fleet-node.sh` onto that machine and run it. It is one file. It does not need Nix, a git checkout, `just`, or a second computer. Before anything is erased it asks the repository owner to approve the node on GitHub (see Self-service enrollment); `--no-enroll` skips that and the node makes its own age key. The person types `ci`, `web`, `cache`, `netboot`, or `devbox`, or passes it with `--yes` (`bash fleet-node.sh ci --yes`, or `FLEET_YES=1`) to run with no typing at all; `--yes` takes the confirmation line as typed and every disk refusal below still applies. The program names that role and the internal disk, and it erases nothing until that line is typed back. A USB, removable, hotplug, or ambiguous disk is refused on Windows, macOS, and Linux. A mounted internal disk is not refused: the disk holding the running system is always mounted, and converting a running machine is the point. The installed hostname stays `<role>[-gpu][-highmem]-<4 hex>` from the hardware id. Do not add a host file, a profile, or a hand-picked name. A machine with no OS cannot download; `bash fleet-node.sh flash` writes the same installer to a USB disk and refuses an internal disk. Removing a node is `fleet-remove` on that node: it withdraws the runner, writes `/nix/fleet-state/withdrawn` (runner units refuse to start while it exists, even after a reboot), and powers the machine off by itself when no job is running. Reinstalling wipes the marker.

An agent can do all of that for the person. Tell it: `Set this machine up as a fleet <role> node by following https://raw.githubusercontent.com/crvouga/workspace/main/packages/fleet/docs/agent-install.md` (`just enroll <role>` prints that sentence with a token in it). The same runbook is inside the downloaded file as `bash fleet-node.sh guide`, which needs no Python. The agent runs `sudo bash fleet-node.sh doctor <role> --json`, which writes nothing, reports every problem at once, and names the exact disk (`erases`). It shows the person the role and that disk, gets an explicit yes, and only then runs `--yes`. `--yes` is never the person's approval. The install runs the same checks first, before any prompt, and refuses on any `FAIL`: not root, not x86_64, not UEFI, no boot tool, an unusable staging filesystem, an unreachable release, too little disk space, and an enrollment token that is spent, expired, or made for another role (checked with Vault's `sys/wrapping/lookup`, which does not spend it). A missing token is a `WARN`, because a node that generates its own key cannot decrypt what the others share. Every run writes a timestamped log with secrets redacted (`<state>/logs/fleet-node-*.log`, newest 20 kept, mode 0600) and prints its path with every failure, along with one `Why:` line and exactly one `Next:` line. Exit 0 is done, 2 is a refused precondition with nothing written, 70 is a bug in the program. The installer keeps its own step log and copies it to `/nix/fleet-state/logs/install.log` on the new node; a failed step prints `FLEET-FAIL` with the line and the log path. The node-side half of approval is `decide.self_enroll`; see Self-service enrollment. On the node, `fleet-node status` is the read-only answer to whether it came up: role, hostname, revision, sync timer, failed units, and the last rolled-back switch. The installer never calls a server to ask permission; after the install, the node's `fleet-agent` reports to the fleet API (below). Do not add a second way to approve a wipe.

## The installer wizard

For a person, not an agent: go to the `fleet-installer` GitHub release, download the file for the computer in front of you, open it, and answer the questions. It runs on Windows (x64), macOS (Apple silicon and Intel), and Linux (x64 and arm64). It is a local web page opened in the browser: `packages/fleet/wizard/` (Python, packaged per OS by `wizard/build.py` with PyInstaller). [docs/installer.md](docs/installer.md) is the user guide. The wizard does two things. It makes an install USB for another computer from any OS, and it converts the running machine in place on x86_64 Linux (`kexec`, the same path as `fleet-node.sh`) and on x86_64 UEFI/GPT Windows (below). macOS cannot restart into the installer, so the wizard says so and makes the USB. Every role includes the native `fleet-installer` and `fleet-node` package, including its Python and kexec dependencies. NixOS uses this package rather than the foreign PyInstaller binary. `fleet-node <role> --reinstall` deliberately replaces an existing same-role installation; the default remains idempotent. Fresh enrollment, disk confirmation and the busy-job refusal still apply. The `fleet-node` and `fleet-installer` flake apps also support existing NixOS machines, without `nix-ld`; ARM64 makes media only.

The web server normally runs without administrator rights and listens on 127.0.0.1 only. Every API request needs this run's secret and a loopback `Host` header. The static page contains no secret or machine facts; the tab retains its API token in sessionStorage so Reload works without putting the token back in the URL. The disk work is `wizard/helper.py`, started through the OS's own prompt (UAC, the macOS password dialog, polkit) with a request file. The helper trusts nothing in it: it re-lists the disks, re-hashes the image, and refuses anything that is not exactly the disk that was planned. The wizard downloads and writes in pure Python (`urllib`, a raw-device write with read-back verification), because Windows has no `dd` or `curl` guarantee. A USB is reported ready only if the read-back hash equals the verified image. Failed writes can leave a USB incomplete; retry the full write. On Windows the helper writes the verified image where it was downloaded; there is no staged copy. Device leases exclude other wizard helpers; confirmations expire after 15 minutes and are single-use. Terminal state and its result are published atomically.

Use `decide.invariant(condition, what, fix, **context)` for every fact the code relies on, never a bare `assert` (`python -O` removes those). An invariant names the broken thing, carries the values that make it diagnosable, and says what to do. It is raised, never swallowed; `main()` stops with exit code 71, and the wizard shows it in the job result. State markers (`installed`, `withdrawn`) are validated on every read, so a corrupt one stops the program instead of being guessed at. Assert at the point of use as well as at the point of decision: the helper repeats the checks the server made. Do not add a test seam that can reach a real disk: `FLEET_WRITE_TARGET` is honored only together with `FLEET_DISKS_FILE`.

Every build must pass its own `--selftest` (page bundled, server up, authentication enforced, helper relaunch, write and read back) before CI publishes it, on every platform in the `installer` job of the root `.github/workflows/ci.yml`. `wizard/ui-e2e.cjs` clicks through the real page in Chromium on every platform. `playwright-bdd` also drives each built download in Chromium on all five platform runners before publication. Wizard jobs install only Fleet dependencies from the frozen root lockfile; typecheck and BDD lint run once in the monorepo CI check, not once per platform. POSIX reinstalls cover all five roles, normal idempotence, explicit hard reinstall, preview, busy refusal, changed disks and failed-handoff recovery with safe stand-ins. Both Linux architectures run the same scenarios against the native Nix package. The NixOS CI and web VMs run the native wizard self-test; the web VM has no nix-ld and additionally exercises the installed CLI hard-reinstall path with simulated disks/firmware/kexec (`tests/native_reinstall.py`). This does not prove an actual firmware handoff or physical disk installation. The macOS and Windows downloads are unsigned: say so in the user guide, do not hide it. Known gaps, so nobody assumes otherwise: the Windows conversion and booting an unsigned GRUB from a raw partition have never run on real hardware; the owner has created and installed the runner App on github.com, and `bdd/features/published.feature` verifies its real registration permission; an install USB cannot carry a role or an enrollment token (the UEFI menu waits for a deliberate role choice, and a node made this way generates its own age key); the elevation prompts (UAC, macOS dialog, polkit) have unit tests for the commands they run but are not clicked through in CI. Devbox USB installs ask for a public key on the console or read devbox.pub from FLEET-KEY. Converting an existing CI node refuses active jobs, withdraws the idle runner through its existing credential and closes its job admission gate before reboot. A failed handoff leaves a withdrawn node that can be reinstalled, including back to CI.

## Converting Windows in place

`decide.stage_windows` (used by `fleet-node.sh` on Git Bash and by the wizard's elevated helper) is the Windows counterpart of `kexec`. [docs/windows.md](docs/windows.md) is the person's guide: the experience, the checklist before a real machine, recovery for every failure point, and what is and is not verified. Windows cannot kexec, so: shrink `C:` by the image size plus 64 MiB (`Resize-Partition`); make a partition of type Linux data and write the verified ISO raw into it at its byte offset through `\\.\PHYSICALDRIVEn`, with the ISO's hybrid-MBR sector zeroed so the partition has one signature, then read it back through a fresh handle and compare (if the disk handle is refused with an OS error, retry once from the start through `\\?\GLOBALROOT\Device\Harddisk{n}\Partition{m}` at offset 0, and name each device in the error); mount the EFI system partition Windows booted from with `mountvol /S` and put the ISO's own `EFI/BOOT/BOOTX64.EFI` (GRUB) at `EFI\fleet\grubx64.efi` and a `grub.cfg` at `EFI\BOOT\grub.cfg` that finds the image by its `/EFI/nixos-installer-image` marker and boots the role's own kernel and initrd with the same command line as the kexec path (minus `findiso=`, with `copytoram`); then install **two independent one-time boot mechanisms, and at least one must verify**: `bcdedit /copy {bootmgr}`, point it at the loader, add it **last** in `{fwbootmgr}` `displayorder` (never first: a firmware that ignores the one-time choice must land in Windows, not in an installer that erases the disk) and set `bootsequence`, verified by `/enum {fwbootmgr}`; and a UEFI `Boot####` load option written directly through `SetFirmwareEnvironmentVariableExW` (`WindowsFirmware`, ctypes, needs `SeSystemEnvironmentPrivilege`) whose device path is `HD(partition, start LBA, size, GUID)/File(\EFI\fleet\grubx64.efi)` of the mounted partition, appended to the end of `BootOrder`, with `BootNext` pointed at it, all read back. Then `shutdown /r /t 15`, and the installer's own downloaded copy (`fleet-installer.iso` in the state folder or the wizard cache, nothing else) is deleted. If neither mechanism verifies, or any later step fails, everything is undone. Every step registers its undo (`WindowsUndo`) before it acts, and a failed step takes back the boot entries, the firmware variables (`BootOrder` and `BootNext` are restored exactly), the files (an existing `grub.cfg` is restored), the partition and the shrink (to the exact original size), newest first. Preflight refuses, before anything changes: not elevated, legacy BIOS, Secure Boot on (the loader is unsigned; the fix names `shutdown /r /fw`), MBR or dynamic disk, sector size other than 512 or 4096, no EFI system partition, the system disk not being the disk to erase, not enough shrinkable space, and too little RAM (the image is copied into RAM: below the image size plus 2 GiB is a `FAIL` on Windows and Linux alike, and a USB install cannot help). The shrink check asks for the room for the download as well while the installer has not been downloaded yet (it lands on `C:` and counts as used space) and is measured again, exactly, after the download. The scripts sent to Windows PowerShell are built by the pure `ps_*` functions in `decide.py` (one line, single quotes only, values through `ps_literal`/`ps_number`/`ps_letter`); `tests/test_powershell.py` parses all of them with the real PowerShell parser and runs them against stand-in cmdlets. It uses `pwsh` or Docker, is skipped with a loud message when neither exists, and fails when `CI` is set. `FLEET_WINDOWS_TARGET` redirects the raw write to a regular file for tests and is refused for anything that is not a regular file, so it cannot reach a real disk; with it set, `open_firmware()` returns no firmware at all unless `FLEET_FIRMWARE_STANDIN` names a directory, which replaces the real UEFI access with files and cannot reach firmware. `fleet-node.sh ROLE --plan` and `doctor` print the exact steps and sizes and change nothing. This path is covered by stand-ins, the PowerShell parser and byte-level tests, and has not been run on a Windows machine.

## Cattle, not pets

Any node is replaceable by any other box with the same role and capabilities. Configurations exist only per role (`ci`, `web`, `cache`, `netboot`, `devbox`), optionally combined with a capability that changes the software (`hosts/ci-gpu.nix`). `hosts/` filenames must be the role plus capabilities from that set.

Never add per-machine configuration or a hand-picked name. No `hardware-configuration.nix`, no disk serial, no `/dev/sdX` or `/dev/nvmeN`, no interface name, no MAC, and no static `networking.hostName`. If a machine seems to need special treatment, add a capability module or fix `modules/hardware/generic.nix`. `scripts/cattle.py check` and `nix flake check` fail the build when those show up in a Nix file.

The generic profile boots a reasonable x86_64 UEFI machine: broad initrd modules, both Intel and AMD microcode, redistributable firmware, and DHCP on every wired Ethernet device by type. aarch64 is a later architecture variant of these same roles, not a board file. Wi-Fi is owned by NetworkManager through `modules/wifi.nix`; wired DHCP stays with networkd. The kernel is the NixOS default.

Disko installs the sentinel `/dev/fleet-install-disk`. The installer requires exactly one internal disk, skipping USB, removable, hotplug, and anything mounted; multiple eligible disks are refused. With `FLEET_AUTO=1` it wipes that disk. A manual `fleet-install ROLE` still requires the path to be typed. Filesystems are labeled `SHBOOT` and `sh-nix` and mounted by label.

### Hostnames

A hostname is `<role>[-gpu][-highmem]-<4 hex>` and is set at boot, not in the Nix config. Examples: `ci-a3f9`, `ci-gpu-7c21`, `ci-highmem-02be`, `ci-gpu-highmem-7c21`, `web-a3f9`. The id is the first 4 hex digits of sha256 of the DMI system UUID, or of the lowest permanent MAC when the UUID is missing. Four digits can collide; the UUID makes that unlikely, and a reinstall of the same box keeps the name. The transient name is applied before SSH, metrics, and runner registration. `/etc/hostname` stays absent. The installer image has no fleet hostname.

GPU is a software capability: `environment.etc."fleet/capabilities.d/gpu"` exists only in the `ci-gpu` closure. high-mem is not a closure. It is MemTotal strictly above `capacity.highMemGiB` (60) times 1024, so a 64 GiB box qualifies and a 32 GiB box does not. The hostname tag is `highmem`. The runner label is `high-mem`.

To add a capability that changes software, add `modules/capabilities/<name>.nix`, import it from `hosts/<role>-<name>.nix`, and allow that extra stem in `HOST_CAPABILITIES` inside `scripts/cattle.py`. Write one tag per line under `environment.etc."fleet/capabilities.d/<name>"` and list it in `TAG_ORDER` when the hostname should include it. A legacy GPU driver is another module, still not a machine. A fact that does not change the closure, such as high-mem, is a threshold in `capacity` and is not a host file.

### Capacity and labels

CI runner count is computed at boot in `scripts/cattle.py`, from `settings/shared.nix` `capacity`: `min(slotMax, max(1, min(cores / perRunnerCores, (MemTotal MiB - reserveGiB * 1024) / (perRunnerGiB * 1024))))` with integer division. Production constants are 4 GiB reserved, 6 GiB and 2 cores per runner, and at most 8. A 16-core 32 GiB machine stays at 4 slots. The closure contains units `slot-1` through `slotMax`; only the live count is started. Workflows target `self-hosted`, `nixos`, and `ci`, plus `gpu` or `high-mem` when they need that capability. They do not target a machine or a model name. `nix build .#nixosConfigurations.ci-gpu` is opt-in. The default CI build does not download the unfree driver.

`http://127.0.0.1:9101/metrics` reports `nixos_node_info` with hostname, role, capabilities, and revision, plus `fleet_sync_rollback` and `fleet_disk_used_percent` when a disk sample exists. It is localhost only. `fleet-drift` compares `/etc/fleet/revision` with `origin/main` and fails when main is older than `drift.maxMinutes` (30) and this node is not on that commit. A newer merge stays in grace. `unknown` fails the unit. The timer stays off while `repo.url` contains `TODO`. A down node cannot report its own silence, which is why `fleet-agent` sends a heartbeat to the fleet API and the API raises the alert when the heartbeats stop. `fleet-disk` fails when `/nix` or `/boot` reaches `disk.alertPercent` (90). Nothing scrapes the metrics port, and `monitoring.pushUrl` is not read. This is not OpenTofu plan drift.

To add an app on the web role, append one attrset to `apps` in `web.nix`: `name`, `domain`, `port`, `containerPort`, and `image` (the OCI image CI already publishes). Set `envSecret` only together with this role's encrypted `secrets/web.yaml`. A null `image` is the local placeholder used until those values are real. Do not invent a domain or an image tag.

## Bootstrap

The installer ISO is built by CI (Test Nix). The workflow uploads `fleet-installer` as an Actions artifact that expires after 14 days, and when a fleet change lands on `main` (the merge queue's `merge_group` run, or the `push` run when the queue is off) it also publishes that ISO as verified 1 GiB parts with a bounded `.parts.json` manifest, its full-image sha256, `fleet-node.sh` and the wizard downloads to the `fleet-installer` GitHub release. The release is the copy a new machine downloads. GitHub rejects individual assets at 2 GiB; `scripts/release-image.py` splits the image, and both download clients assemble the parts while checking each part and the complete image. Never flash an individual part. `scripts/fleet-node.sh` is one file: it fetches that release, asks for `ci`, `web`, `cache`, `netboot`, or `devbox`, names the internal disk, and reboots into the installer only after that line is confirmed. It does not need Nix, `gh`, or a checkout. If the download is missing or expired, it exits non-zero, writes nothing, and prints one next step. A second fetch of the same release asset is the same bytes. `ci-gpu` is not on the image. The boot menu lists the five roles. The UEFI boot menu waits for a deliberate choice, and labels every role as erasing the internal disk. `fleet.role=` on the kernel command line selects the closure. A later `fleet.role=` wins, which is how the web, cache, and netboot menu entries override the default. The live image then runs `fleet-auto` and wipes the chosen internal disk. `sshKeys` may stay empty. `just bootstrap ROLE IP` only forwards a keyboard over SSH when a key is configured, and it sets `FLEET_AUTO=1`. It does not build Nix and it does not read an age key. `just fetch-iso` is the legacy 14-day artifact download. Do not use it to add a node.

The private key is created at `/nix/fleet-state/secrets/age.key`. The public key is printed on the console and stored in `age.pub`. A filesystem labeled `FLEET-KEY` supplies `<role>.age` when the file is already there, and receives a newly generated key when it is not, so the next node of that role can decrypt the same sops file. This package does not generate a key into git. Without a token, a node asks to be approved (below); `--token-file PATH` (or `FLEET_ENROLL_TOKEN`) skips that and replaces the `FLEET-KEY` USB: the token is a single-use Vault response-wrapping token that holds the role key at `secret/data/fleet/<role>`, field `age_key`. `just setup --repos ...` does `just fleet-keys` (the missing role keys: private keys to the vault root's git-ignored `fleet-age-keys.auto.tfvars.json`, public recipients to `.sops.yaml`) and the rest of the one-time setup. `just enroll <role>` still prints the one line to paste on a new node when someone with Vault access wants to hand a token over by hand: it downloads `fleet-node.sh` and runs it with `FLEET_ENROLL_TOKEN` set. It goes onto the installer command line as `fleet.enroll=`, is unwrapped by `fleet-install` before the disk is touched, and is never printed. A refused or spent token wipes nothing. A token is never an argument (`--token VALUE` is refused). The `FLEET-KEY` volume still wins when it holds `<role>.age`. The path is owned by the vault OpenTofu root (`vault_kv_secret_v2.fleet`, input `fleet_age_keys`, a complete map of role to `AGE-SECRET-KEY-` value, each distinct). Change it there with a reviewed plan, never with `bao kv put`. Declaring it is not applying it. The netboot ramdisk does not carry the role closures. TODO: the netboot host does not serve this ISO, so a `reinstall.nodes` or `reinstall.roles` flag does not install a node. Reinstall with `fleet-node.sh` on the machine.

The ISO host key is ephemeral. The installed host key is `/nix/fleet-state/ssh/ssh_host_ed25519_key`, generated on the machine. The console prints its fingerprint after reboot. Steps that stay physical are in `docs/checklist.md`.

To rotate a role age key, follow `secrets/README.md`. The new private key is encrypted to the current key as the sops secret `age-key-next`. Set `rotateAgeKey = true` on that role in the same commit. The node installs it to `/nix/fleet-state/secrets/age.key` when it pulls. A second commit drops the old recipient. Do not SSH the key onto the node. `ci-gpu` uses the `ci` key. This package does not generate keys into git.

To reinstall a node, run `fleet-node.sh` on that machine. A `reinstall.nodes` or `reinstall.roles` flag does not install a node, because the netboot host does not serve an installer that can finish. TODO: no smart PDU model is selected and this repo does not power-cycle a node. A power cycle is physical until that integration exists. Do not invent a vendor, a host, or a credential.

## Self-service enrollment

A node cannot ask Vault for its role key: the release is public. The repository owner approves it with one click, and nothing is stored in GitHub. `decide.self_enroll` makes an X25519 key pair in memory and opens `issues/new?title=fleet-enroll+<role>` prefilled with the role and the public key. `.github/workflows/fleet-enroll.yml` (a byte copy of `workflows/fleet-enroll.yml`) runs on `issues: opened` only when `author_association == 'OWNER'` and the title starts with `fleet-enroll `. `scripts/enroll.py` logs in to Vault with the job's GitHub OIDC token; the `fleet-enroll` JWT role is bound to `job_workflow_ref` of that file on `refs/heads/main`, and its policy (`packages/vault-service/config/policies/fleet-enroll.hcl`) allows only a read of `secret/data/fleet/+` with `min_wrapping_ttl`, so Vault refuses an unwrapped read and the workflow never holds an age key. The script asks for a 1-hour wrapping token, seals it to the node's public key (ephemeral X25519, HKDF-SHA256, an HMAC-SHA256 keystream, an HMAC tag; pure Python in `decide.py`, checked against RFC 7748), and the workflow comments `fleet-sealed: <ciphertext>` or `fleet-error: <fix>` and closes the issue. The node polls the issue list and comments with conditional requests, accepts only comments from `github-actions[bot]`, opens the blob with its private key, accepts a token only for its own role, and checks it with `sys/wrapping/lookup` before it asks anyone to confirm the erase. Nothing is erased while it waits (`FLEET_ENROLL_WAIT`, 15 minutes). The wizard does the same after "Erase and install" and the job log shows the link; Cancel stops the wait. The `fleet-enroll` role and policy are declared in the inventory and apply only through the reviewed vault plan. Do not add a bot token, a shared secret, or a callback server for this.

## One-time setup

`just setup` (or `just setup --repos owner/private[,owner/other]`, `scripts/setup.py`, once, by the owner): role age keys; the runner GitHub App from a manifest (the owner presses Create and Install; the one-time manifest code and the App key are kept at `~/.fleet/setup-github-app.json`, mode 0600, until the run finishes, so an interrupted run resumes without creating a second App); `secrets/fleet.yaml` encrypted to the ci recipient only; `settings/github.json` filled in and the encrypted secret enabled in `fleet.nix`. Repositories come from that central JSON file or an explicit `--repos` override and are never guessed: a public one would run strangers' pull requests on the fleet. It ends by printing the two reviewed steps (merge, then plan and apply the vault root). Do not run the apply from this package.

Bootstrap GitHub App IDs, scope and repository fallback belong only in `settings/github.json`, imported by `fleet.nix`. Setup and the read-only runner health check read that same JSON. Never copy repository-specific values into Python, Nix modules or workflows. Runtime routing belongs in the existing API/Postgres `runners.repositories` setting; secrets stay in Vault and the role-encrypted files.

## Fleet API and dynamic configuration

`packages/fleet-api` (https://fleet.chrisvouga.dev, Railway, Docker) is the control plane: every node's `fleet-agent` reports a heartbeat and receives its dynamic settings. Read [its README](../fleet-api/README.md) and the wire contract [PROTOCOL.md](../fleet-api/PROTOCOL.md) before changing either side. Rules that hold on this side:

- **Data, never code.** The API sends typed settings (`src/config/schema.ts`); `scripts/agent.py` and `scripts/fleetconf.py` interpret the keys they know and ignore the rest. Nothing a server sends is executed, written into a unit, or used as a path. Keep it that way: a compromised API must not be able to run code on the fleet. There is no command channel and none may be added.
- **The fleet works without it.** No API, a corrupt cache, or a TODO `fleetApi.url` means the agent exits quietly and every value comes from the image. Reporting never blocks `fleet-sync`, a runner, or a boot.
- **Git still decides what a machine is.** Roles, closures, the GitHub App identity, the web apps and anything that changes a closure stay in git. The API changes how an existing closure behaves, within bounds it validates (`docs/dynamic-config.md` lists every key, what the node does with it and its default).
- **Credentials.** A node generates its own secret (`/nix/fleet-state/agent/node.secret`) and registers. A role token (`/nix/fleet-state/agent/role-token`, delivered by `fleet-install` from the single-use wrapped Vault document, field `api_token`) makes registration automatic; a machine without it waits under Pending in the dashboard until a person approves it. Never print either, and never put either in a command line.
- **Removal.** `fleet-node remove` calls `fleet-agent retire` (best effort, short timeout) so a removed machine is retired on the dashboard, not reported offline forever.
- **End-to-end test.** `tests/test_e2e_chain.py` runs the real installer scripts, the approval script, the agent and the real API on a throwaway Postgres, once against a process and once against the Docker image. Change the protocol, an agent behavior, an installer step or the schema and this test must pass. CI runs it as `fleet-e2e` and requires it.

## Sync and rollback

comin is not in nixpkgs at the pinned revision `7c8764b7`, and this flake does not add an unlocked input. `modules/sync.nix` and `scripts/fleet-sync.sh` are the pull agent. Do not also enable `system.autoUpgrade`.

Every role polls `main` over HTTPS. There is no `deploy` branch and no `canary` branch. The timer stays off while `repo.url` contains `TODO`. The poll is 300 seconds plus 30 seconds of jitter. The node runs `nix build --max-jobs 0` and switches only when that role's toplevel is already in the binary cache. A miss exits and the timer retries. The node does not build locally. While `binaryCache.url` is empty or contains `TODO`, it waits the same way. `self.rev` is null on a dirty tree. `system.configurationRevision` is `self.rev`, or `unknown`. It is published at `/etc/fleet/revision` and `http://127.0.0.1:9101/metrics` (localhost only).

A kernel, initrd, or module change resolves the stable id and sleeps for `cksum(stable id) % delayMaxSeconds` (default 7200; 0 disables) before draining, then applies the boot generation and reboots. Missing identity never drains. CI uses `fleet-drain` with mandatory automatic `fleet-resume`; a failed update restores admission, and failed resume stays marked for agent retry. Other changes switch in place. After every switch, including a bootloader update, probes require GitHub/cache connectivity, a loadable sync service and a healthy timer. Failure restores the previous generation, persists safe diagnostics across reboot, exits non-zero and retries on the next timer. A failed reboot request also restores the previous boot generation. An unchanged revision avoids another switch but still verifies the recovery channel.

systemd-boot keeps 8 generations and waits 5 seconds. `scripts/boot-count.sh` marks the newest entry with 3 tries; this pin has no boot-counting option. `fleet-boot-health` gates `boot-complete.target` and blessing on GitHub/cache connectivity and the update timer. Failed counted upgrades reboot only when a fallback entry exists; a first install stays alive and retries. Healthy-boot and update GC roots protect the previous usable closures from weekly 14-day collection. Runtime/reboot watchdogs remain 30 seconds/5 minutes. The volatile journal is capped at 256M. Real EFI fallback still needs hardware acceptance; fixture tests are not proof of firmware behavior.

Git read access is `repo.auth`: `none`, `ssh` (`/run/secrets/git-read-key`), or `token` (`/run/secrets/git-read-token`). Encrypt that credential separately into each role's sops file. Any auth other than `none` requires that role's `secretsFile`.

The shared update cache is the cloud `turborepo-remote-cache` service's public `/nix` namespace backed by R2. It must remain independent of physical Fleet nodes. The Vault OpenTofu root owns the Ed25519 signing key and isolated CI credentials; only its real public key is pinned in `settings/shared.nix`. Never generate signing keys at service startup or put private material in images. Do not enable `cache.remote` alongside the shared cache. The physical Attic role is optional; its storage is bind-mounted from `/nix/fleet-state/attic`, and it stays off while its own `secretsFile` is null.

The root `.github/workflows/ci.yml` is the single pipeline definition. It runs on `ubuntu-latest`, never on this fleet, so a broken fleet can still be fixed by merging. It has no `on.paths` filter. The `Fleet` job always reports a status. When the diff does not touch this package, that job succeeds without building. A pull request that does touch it evaluates all outputs with `nix flake check --no-build`, then builds every flake check across four concurrent GitHub-hosted jobs: role closures and static checks; runtime VMs; lifecycle, follow-up and netboot VMs; and the offline installer ISO. `scripts/ci-checks.py` discovers the check names from the flake, assigns each once, and sends new checks to the roles group. Each group has a 20-minute timeout. VM groups keep at most two concurrent builds with two cores each, keeping QEMU guests inside the 16 GB GitHub-hosted runner. Non-VM role/image groups may use four builds and four cores so static derivations and compression use the whole runner. All groups must succeed. Evaluate through Git flake references (`.#...`) and build the resulting exact derivation paths; `path:.` loses `self.rev` and creates different closures with revision `unknown`. Runtime and lifecycle checks may reuse only exact-derivation success records; roles and images must materialize outputs. Manual runs ignore those records. The ISO is built once and uploaded without artifact compression only for publication events, with one-day retention. ISO and netboot Squashfs use zstd level 3 to avoid minutes of level-19 compression. `follow-up` checks that a node which has switched can pull and switch to the next commit, and that a failed health check restores the previous one. It is required by the lifecycle group. There is no separate GitHub status name. `ci-gpu` is evaluated and is not a default build.

`Fleet cache` signs and publishes all five role closures on GitHub-hosted runners for every exact main commit and merge group, with scheduled/deployment recovery triggers. Main publication is required even for unrelated commits because `self.rev` changes, and this personally owned repository cannot currently enable merge queues. NARs publish before signed narinfo pointers. Native Nix verifies every signature; an authenticated artifact records the exact revision, closure paths and pinned public key. Release installer checks that proof after Nix and installer checks. Public cache reads are independently mandatory in live-image preflight before erasure; first deployment must not deadlock waiting for the new HTTP route before it can deploy. A miss leaves running nodes on their current generation and their timers retry. No physical cache machine, repository cache variables, or hand-entered Attic token is needed.

A rollback is a revert pull request through the same checks and the same queue. The previous commit's systems are already in the cache. systemd-boot keeps `bootGenerationLimit` generations (8), selectable from the console. There is no force-push rollback.

Automatic catch-up is a required release contract. Keep `fleet-sync` enabled at
boot, schedule retries after attempts finish, and let an updater finish when its
own unit changes. `checks.update-units` covers every role; `checks.follow-up`
must exercise timer-driven offline/reboot recovery and real generation switches.
See [update reliability](docs/update-reliability.md) for fault scenarios and
the distinction between fixture substitution and physical-machine acceptance.

`main` requires a pull request, the `Check` and `Fleet` checks (with a temporary `Required` compatibility status until the ruleset migration is applied), and the merge queue. Direct pushes and force pushes are refused. That ruleset is OpenTofu in `packages/infra` (`inventory.tf.json` and `foundation/repository.tf`). Declaring it is not applying it. Apply a reviewed plan. Do not apply it from this package.

One path changes a node. Open a pull request, let `Check` and `Fleet` pass on GitHub-hosted runners, and let the merge queue land it on `main`. Nodes pull that commit. Do not push `main` directly, force-push it, or change a node by hand.

The Update job in `.github/workflows/maintenance.yml` runs once a week. It runs `nix flake update` in this package and opens or updates one pull request on `chore/fleet-flake-lock`. That pull request uses the same checks and the same queue. It does not push `main`.

This package does not own GitHub configuration, buckets, billing, DNS, or other workspace infrastructure. Every dependency is pinned in `flake.lock`. Do not update it implicitly. Do not commit tokens, age private keys, or plaintext secrets.

Run `bun run --filter @pkgs/fleet check` for portable checks. From this package: `just check`, `build-node`, `build-web`, `build-cache`, `build-netboot`, `build-iso`, `vm-test`, `fetch-iso`, `flash-usb ISO DEVICE`, `bootstrap ROLE IP`, and `status NODE`. `fetch-iso` and `flash-usb` do not need Nix. `bootstrap` does not build.

`flash-usb` and `bootstrap` are destructive. Obtain explicit human approval identifying the disk before executing them. An interactive confirmation is an additional check, never authorization. Do not execute a generated installer or a VM against physical disks. Never print secrets, place them in CLI arguments, or copy plaintext credentials into the Nix store. Never change GitHub settings, secrets, or billing without explicit approval. Runtime registration uses the configured GitHub App; tokens remain in `/run`.

CI nodes drain through `scripts/drain.sh` (`fleet-drain`) before a kernel reboot. Restrict runner projects to private trusted code, require `nixos` and `ci` routing labels, and never run fork PRs or `pull_request_target` on the runner fleet. Keep credentials root-only. Inspect actual upstream module source at the locked nixpkgs revision when changing module behavior. A local portable check is not `nix flake check` and is not a VM test. Report when those were not run.
