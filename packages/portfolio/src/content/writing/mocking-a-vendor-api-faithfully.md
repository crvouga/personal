[Mockingbird](https://github.com/crvouga/mockingbird) is a set of emulators for vendor APIs: Stripe, Twilio, Junction, PostHog and more than a hundred others under [`packages/service/`](https://github.com/crvouga/mockingbird/tree/main/packages/service). An emulator is only useful if it behaves like the vendor. A mock that returns `200` where Stripe returns `400` lets a bug through to production that a test suite was supposed to catch. This post covers how Mockingbird tests that, and where the testing is thinner than the design.

## Two properties, one generator

[`docs/TESTING.md`](https://github.com/crvouga/mockingbird/blob/main/docs/TESTING.md) states the design in two lines:

1. **Self-parity** runs in CI with no credentials. Two independent emulator instances must agree after every command, and every emulator response must conform to the spec.
2. **Live parity** (`bun run parity`, sandbox keys required) runs the same walk against the real sandbox and a fresh emulator.

Both use the same generator, built on [fast-check](https://fast-check.dev/). Both canonicalize responses first, stripping volatile ids, timestamps and tokens, and then compare structure. A failure shrinks to a minimal walk and prints a seed, so `FC_SEED=12345 bun test` replays it.

## Where the commands come from

The input is the vendor's OpenAPI document. Stripe's [`openapi.yaml`](https://github.com/crvouga/mockingbird/blob/main/packages/service/stripe/openapi.yaml) is generated by `scripts/vendor.ts` from a pinned commit of `stripe/openapi`, and its header says "Do not edit by hand." It is a subset: 126 operations, of which 114 have parity enabled.

The spec carries annotations the generator reads. `x-mockingbird-resource` marks an id field, so the runner can pair the id the real side returned with the id the emulator returned. `x-mockingbird-resource-ref` marks a parameter that refers to one. `x-mockingbird-volatile` marks a field like a `client_secret` as a token to strip before comparing. `x-mockingbird-parity-header` marks the response headers that must match.

## How a walk runs

The [`packages/parity/runner` README](https://github.com/crvouga/mockingbird/blob/main/packages/parity/runner/README.md) describes each walk. The runner picks operations that are supported and parity-enabled. fast-check generates a sequence of commands, 25 walks of up to 30 commands by default. References are symbolic (`note #1`) and resolve to each side's own ids. About 15% of bodies are invalid by exactly one constraint, and about 8% of references point at an id that does not exist. Error paths get walked, not only happy paths.

For each command, the runner sends the request to the real side, then to the emulator. The emulator's status must be one the spec declares, and its body must validate against the response schema. Both exchanges are canonicalized and diffed on status, declared headers and body. A divergence throws a `ParityError` whose kind is `mismatch`, `mock-conformance`, a transport error, `latency` or `webhook-mismatch`.

## Self-parity in practice

[`stripe.property.test.ts`](https://github.com/crvouga/mockingbird/blob/main/packages/service/stripe/stripe.property.test.ts) shows the self-parity setup. The "real" side is a long-lived `StripeAPI` with a fixed clock. The emulator side is a fresh `StripeAPI` per walk. The test runs 40 walks of up to 25 commands, with unsafe operations included. A second test replays eight pinned seeds with coverage bias and asserts that, together, they exercise every parity-enabled operation.

Comparing an emulator with itself sounds circular. It catches two real classes of bug. The first is hidden state: if behavior depends on anything other than the command sequence, two instances drift apart. The second is spec conformance, which needs no second side at all.

The repository keeps a record of what this finds. [`PARITY_FAILURE_SEED_REGISTRY.json`](https://github.com/crvouga/mockingbird/blob/main/PARITY_FAILURE_SEED_REGISTRY.json) says "Add every newly discovered failing seed here before fixing it" and has 53 entries. One Stripe entry is a conformance failure where the spec disagreed with itself: a 40,000-character product description passed the request schema but failed the vendored response schema, which capped it at 5,000. Another records a bug in the harness: invalid bodies were never generated for form-encoded operations.

## Live parity in practice

Stripe's live script, [`scripts/parity.ts`](https://github.com/crvouga/mockingbird/blob/main/packages/service/stripe/scripts/parity.ts), points the real side at `api.stripe.com`. It accepts only `sk_test_` or `rk_test_` keys, spaces requests by 40 ms, redacts secrets from reports, and deletes or archives the real resources it created after each walk. It excludes operations that would register a live webhook endpoint. The runner refuses any host not in `allowedHosts` before sending.

This is the half that can prove the emulator matches Stripe rather than matching itself. The registry has an open Stripe entry from a live run: `GetPaymentMethods` with an empty `customer_account` returned `400 parameter_invalid_empty` from Stripe and `200` with an empty list from the emulator ([run 37247323827](https://github.com/crvouga/mockingbird/actions/runs/37247323827)). Self-parity could not have found that. Both emulator instances agree on the wrong answer.

## How often live parity runs

Live parity spends a vendor's rate limit, so each service declares a tier in its `package.json` as `mockingbird.parityTier`. `hot` runs on each PR that changes the service's dependency graph. `warm` runs weekly from the `schedule:` in [`parity.yml`](https://github.com/crvouga/mockingbird/blob/main/.github/workflows/parity.yml), Mondays at 06:17 UTC. `cold` runs only when someone dispatches it, usually with `bun run parity:remote -- <service>`. A service with no tier is cold.

Today every service is cold. Of the 127 packages under `packages/service/`, 111 declare `cold` and 16 declare nothing. The weekly warm run therefore resolves to an empty list. [Run 40328466959](https://github.com/crvouga/mockingbird/actions/runs/40328466959) on 2026-10-26 shows `Plan` succeeded and `Live parity` was skipped, and the run reports success.

The only scheduled live check is [`verify.yml`](https://github.com/crvouga/mockingbird/blob/main/.github/workflows/verify.yml), which runs `mockingbird-junction verify` against the Junction sandbox daily. It covers one service. Its [2026-10-26 run](https://github.com/crvouga/mockingbird/actions/runs/40356453055) failed with "Junction sandbox returned HTTP 402 Payment Required", and every scheduled run listed from 2026-10-06 onward failed. ## What I'd change

The design is sound. The schedule does not match it. Self-parity runs in the PR workflow for every affected package. Live parity, the half that compares against the real vendor, runs on no schedule for any service except Junction, and the Junction check has been red for weeks. A green weekly Parity run that tested nothing looks the same as one that tested everything.

- Promote a few services with stable sandboxes, Stripe first, to `warm`. The docs already say promotion is one value in `package.json`.
- Make the scheduled Parity run fail, or at least warn, when the warm tier resolves to zero services.
- Treat a red Verify run as an incident with an owner. A 402 is an account problem, not a parity result, but it still means nothing is being checked.
- Publish each service's last live parity date next to its tier, so a user can see how recent the evidence is.
