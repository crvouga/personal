# crvouga/personal — infrastructure guides for agents (index)

> `crvouga/personal` documents two **separate** kinds of infrastructure in two **separate** guides. They share no sections and must never be mixed. Pick exactly one guide for each task, using the table below. This index holds no setup or integration instructions.

| Your task is about… | Guide | URL |
| --- | --- | --- |
| A **developer machine**: installing or updating tools (mise, Bun, Node, Docker engine, CLIs), workstation config, the `personal` CLI, the Ubuntu developer fleet / `fleet-sync`, T3, the private fleet AI proxy (CLIProxyAPI), Beszel, Turborepo caching, disposable test databases | **LOCAL development infrastructure** | https://www.chrisvouga.dev/llms-local.txt |
| An **app's cloud resources**: Vault/OpenBao secrets, `DATABASE_URL` / PostgreSQL, the R2 object store, hosting on Railway with GHCR images, DNS/TLS on `*.chrisvouga.dev`, GitHub OIDC in CI, Google sign-in via the auth relay, `[hosting]` / `[secrets]` / `[database]` / `[storage]` / `[auth]` issues | **CLOUD app infrastructure** | https://www.chrisvouga.dev/llms-cloud.txt |

## How to tell them apart

- **Local** = runs on, or configures, a computer someone develops on. Owned by mise, `packages/workstation` and `packages/fleet`. Never provisions anything in the cloud.
- **Cloud** = OpenTofu-managed resources that hosted apps use. Owned only by OpenTofu in `crvouga/personal` and changed only through a GitHub issue and a reviewed PR. Never configures a machine.
- **`dev` does not mean local.** The Vault `dev` config, the `dev` bucket, the `dev` `DATABASE_URL` and the nonproduction auth relay are **cloud**. Reading them from a laptop (`personal infra-vault run`) is a cloud task.
- **Machines consume cloud credentials; they do not own them.** A fleet node logging into Vault is a local task that reads a cloud secret. Changing the secret, its policy or its token is a cloud task.
- **A developer machine is never a hosting target**, and a hosted app never depends on a developer machine.
- A task that seems to need both is two tasks. Do the local part with the local guide and the cloud part with the cloud guide, and keep their commands, credentials and terminology apart.

## Linking from another project

Link only the guide(s) your project needs, with their labels, from `AGENTS.md` / `CLAUDE.md`:

```md
Cloud app infra (Vault, PostgreSQL, R2, hosting, Google sign-in): https://www.chrisvouga.dev/llms-cloud.txt
Local dev machine setup (toolchain, fleet, AI proxy): https://www.chrisvouga.dev/llms-local.txt
```

Re-fetch instead of trusting a cached copy. Source snapshots on `main`: https://raw.githubusercontent.com/crvouga/personal/main/llms-local.txt and https://raw.githubusercontent.com/crvouga/personal/main/llms-cloud.txt. If anything in either guide disagrees with OpenTofu or `mise.toml` in `crvouga/personal`, those win; tell the human the guide is stale and open an `[infra]` issue.

## Maintaining these files (agents working inside `crvouga/personal`)

All three files are generated by [`scripts/llms-txt.ts`](https://github.com/crvouga/personal/blob/main/scripts/llms-txt.ts): this index from [`scripts/llms-txt.template.md`](https://github.com/crvouga/personal/blob/main/scripts/llms-txt.template.md), the local guide from [`scripts/llms-local.template.md`](https://github.com/crvouga/personal/blob/main/scripts/llms-local.template.md), the cloud guide from [`scripts/llms-cloud.template.md`](https://github.com/crvouga/personal/blob/main/scripts/llms-cloud.template.md). Never edit the generated copies. Put local-machine content only in the local template and cloud content only in the cloud template; `bun run check:llms` fails when either guide contains the other's markers.
