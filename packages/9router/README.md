# 9router on Railway

The unmodified [upstream 9router image](https://github.com/decolua/9router/blob/master/DOCKER.md) serves https://9router.chrisvouga.dev. Configure providers, combos and clients through its dashboard. This package adds only [Litestream](https://litestream.io/guides/docker/) and a startup lock; it has no application fork, local daemon manager, tunnel connector or dependency patches.

SQLite lives at `/tmp/9router/db/data.sqlite` on the container's ephemeral filesystem. **Do not attach a Railway volume.** Litestream restores from `9router/sqlite` in the existing shared production R2 bucket before starting the app, replicates WAL every second and runs a final one-shot replication after the app closes on graceful shutdown. Only Postgres and blob storage retain durable state. Logs, certificates and other runtime files are disposable; the supported hosted workflow uses the web dashboard and provider OAuth/API connections, without local MITM tools.

The wrapper holds the shared Postgres session advisory lock `(923, 20128)` across restore, service lifetime and final replication. It creates no tables or schemas. A replacement waits for the old writer to exit before restoring, preventing independent SQLite databases from overwriting the same replica. Loss of the lock connection kills the process group immediately. Abrupt host loss can lose changes not yet uploaded; replication is asynchronous, not a zero-loss transaction log. R2 failures during restore stop startup rather than silently creating empty state. An empty replica is allowed on first launch.

Railway runs one replica, always on, with zero overlap and a 60 second drain budget. Its **deployment** healthcheck is disabled so the waiting wrapper becomes active and Railway terminates the old writer; otherwise the lock handoff would deadlock. Public inventory health checks still probe `/api/health`. Updates have a brief interruption while the new process restores. Do not enable sleeping, multiple replicas, or a deployment healthcheck without changing this protocol.

All service, DNS and secret configuration belongs to the [OpenTofu inventory](../infra/tofu/modules/inventory/inventory.tf.json). CI builds this package's Dockerfile and publishes/deploys it with the other workspace images. `DATABASE_URL`, the existing four router credentials (exposed as `INITIAL_PASSWORD`, `JWT_SECRET`, `API_KEY_SECRET`, `MACHINE_ID_SALT`) and shared `S3_*` values come from the production Vault document through OpenTofu. No new bucket or database is needed.

## Cutover

1. Preserve any existing local SQLite data before retiring the local process. Stop its writers and use SQLite's backup API to make a consistent backup; do not copy an active WAL database. No local state is tracked by this repository. If existing state exists, seed the Litestream prefix with that database before the first hosted launch, using the same pinned Litestream version and credentials. Never seed while Railway owns the writer lock.
2. Publish the image, then review/apply saved OpenTofu plans in the normal foundation → vault → fleet order. Foundation forgets the existing DNS record without deleting it and retires the old tunnel ingress to a 404. Fleet imports that exact record and updates it to Railway. The adopted tunnel identity and its existing credentials remain protected for later explicit decommissioning; no tunnel resource is replaced or destroyed.
3. Check `/api/health`, configure a harmless setting, redeploy, and verify that it survives restore. Run `bun run health --only services,storage,images` after deployment.

Validate runtime handoff with `bun run --filter @pkgs/9router test`, infrastructure with `bun run check:infra`, and regenerate the consumer guide with `bun run llms:sync`. Docker context is this directory; `.dockerignore` excludes local credentials and data.
