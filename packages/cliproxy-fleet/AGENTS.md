# CLIProxyAPI package

This package owns reproducible local deployment and runtime operations. The proxy runs only on the fleet **manager** (`manager.id` in `packages/fleet/definition.json` v3: the macOS MacBook Air, Docker Desktop + per-user launchd agents, never sudo). **Workers** are clients and never host it; `fleet_sync.py` reports a worker install (`PROXY_DUPLICATE_OWNER` / `PROXY_DECOMMISSION_PENDING`) and never stops it. The Linux systemd backend (`/opt/cliproxy-fleet`) is legacy, kept only to fence, back up and decommission the previous host via `docs/migration.md`. Keep platform dispatch in `scripts/cliproxy_host.py` explicit and small.

Authored code/config templates must be committed here before installation. Never patch an installed root (`~/Library/Application Support/cliproxy-fleet` or `/opt/cliproxy-fleet`); its operational paths, LaunchAgents and units must link to clean Git-tracked code at the recorded deployment commit. Do not render executable wrappers, plists or units, or copy code outside source control; `launchd/*.plist` are tracked as-is and reference the default manager root via `$HOME`. Client commands must link to the tracked launcher. Preserve `state/` during updates, and keep it out of Git. Secrets live in Vault and encrypted backups.

Do not add cloud provisioning, tailnet policy mutation, Vault writes or secret seeding here. Those belong to the repository's OpenTofu roots. Runtime login, token renewal, local advertisement of existing Services, secret reads and backup operations are allowed. Never print credentials or activate a second copy of provider/Tailscale state during restore tests.

Check with `bun run --filter @pkgs/cliproxy-fleet lint` and `test`. Tests must be offline and must not read the production Vault token or deployment; fake `launchctl`, `scutil` and Docker Desktop detection. Installation uses committed blobs and records a manifest; cover state preservation and drift detection when changing that boundary.

Model health lives in `models.json` (declarative) and `scripts/modelhealth/` (generic engines); read `docs/model-health.md`. Adding a model, capability or fault scenario is a `models.json` change, never model-specific code. Never report an untested capability as healthy, never retry inference, never log keys or prompt text, never send management keys from health checks, and keep live inference out of offline tests (use the emulator). Do not claim live health without a successful `live`-target report. Routing is fill-first (drain one account, then the next); keep `config.template.yaml`, `models.json` `routing`, the emulator and `validate-config --require-fill-first` in step, and never claim the live proxy uses it until the host monitor is clean.
